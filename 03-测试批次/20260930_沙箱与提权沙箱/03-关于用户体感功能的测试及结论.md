# 关于用户体感功能的测试及结论（沙箱/权限隔离）

> 本篇**不打术语**，写给"要判断这东西能不能用、好不好用"的人看。
> 技术版（含代码、规格引用、证据索引）在同目录 `01-缺陷单.md` 与 `02-沙箱与提权沙箱-测试记录.md`。
> 被测版本：TPT Work，包体 `app.asar` = 253,660,790 B（2026-09-29 21:50:02），`tpt-work.exe` 版本号 `0.1.3.0`
> 测试日期：2026-09-30 · 方式：在真实软件界面上一步步操作 + 逐个命令实测 + 直接看磁盘和文件夹权限

## 一、先说清"隔离"到底在管什么

AI 能**读**你电脑上几乎任何文件（**读不限制**），被限制的只有**"写"和"删"**。
也就是：它只能在你选的**项目文件夹里**改动文件，**出了这个范围就该被拦住**。

所以本次测试就一句话：

> **我让它改 A 处（项目文件夹内）和 B 处（项目文件夹外），它到底能不能动手？**

## 二、四个档位，用户能选到的是什么

软件里你能选的是这 4 个（在输入框下方那个 `工作区内修改` 的小标签里点开）：

| 界面上显示的 | 用户理解 |
| --- | --- |
| **仅可查看** | AI 只能看，不能改 |
| **工作区内修改** | AI 只能在当前项目文件夹里改（**默认就是这个**） |
| **完全权限** | 不限制，AI 哪里都能改 |
| **Auto review**（带 EXP 标记） | 名字听起来像"自动审查"，实际见下文第三-2 条 |

## 三、实测结果

### 3-1 四个档位对照表

| 档位 | 让它改**项目文件夹里** | 让它改**项目文件夹外** | 判定 |
| --- | --- | --- | --- |
| **仅可查看** | ❌ 拦住（新建 / 修改 / 删除全拒） | ❌ 拦住 | ✅ **正常** |
| **工作区内修改**（默认） | ✅ 允许（新建、修改、删除、含 200 个文件的子目录都正常） | ❌ 拦住（连 `C:\Windows\Temp`、你的用户目录都拦） | ✅ **正常** |
| **完全权限** | ✅ 允许 | ✅ **允许**（真的是完全放开） | ✅ 符合它的定位 |
| **Auto review (EXP)** | ✅ 允许 | ✅ **允许**（同样是完全放开） | ⚠️ **名不副实** |

### 3-2 顺带测到、都表现正常的几点

| 测试点 | 结果 |
| --- | --- |
| 切到「完全权限」「Auto review」时**有没有风险提醒** | ✅ 两个都会弹确认框，**必须勾"我已了解风险"才能点确定** |
| **切换是否立刻生效** | ✅ 从「完全权限」切回「工作区内修改」后立刻再试写项目外，**马上被拦住**，没有"切了没生效" |
| 「仅可查看」是否真的一点都不能写 | ✅ 项目内、项目外**全部拒绝**（我直接查了磁盘确认文件没被创建） |
| 越界时有没有告诉 AI"你可以申请放宽" | ✅ 有，而且提示里写清了"要申请人批准" |

### 3-3 一个容易被误会成"安全"的细节

AI 除了用命令行，还会用它**自带的文件写入功能**。我专门测了这条 —— **它同样被拦住**。
也就是说限制**不只管命令行，自带功能也管**，这一点是好的。

## 四、三个你会真实感受到的问题

### 4-1 【最要紧】用普通文件夹当项目，AI **连命令都跑不起来**

**怎么发现的**：我拿 `D:\tpt-workspace\0929\p1` 和 `p2` 当项目，两个都失败，报错是内部术语：

> `SetNamedSecurityInfoW failed (Win32 5)：grantWrite(D:\tpt-workspace\0929\p1)`

**用大白话解释**：这个限制功能需要给项目文件夹**加一个"权限标记"**；加这个标记需要**像"文件夹所有者"才有的那种高权限**。而你在 `D:\` 下随手新建的文件夹，默认权限是"普通用户可修改"，**不含那种高权限** → 标记加不上 → **整个项目下的 AI 命令全部拒绝执行**，连 `echo hello` 都不行。

**对照组**：产品自己放任务的目录（`C:\Users\你\.tpt-work\tasks\...`）权限给得足，**那里一切正常**。

**为什么这件事严重**
- 用户最可能建文件夹的地方（`D:\` 这种盘根下）**刚好就是会出事的类型**；
- 报错是内部术语，**用户看不懂**，也没有"点一下修复"的按钮；
- 表现是"AI 完全不能干活"，容易被误认为"AI 坏了"。

**⚠️ 而且它自带的"修复/诊断"工具救不了**
那个诊断脚本要用一个叫 `icacls` 的命令，**在产品自己启动的环境里找不到这个命令** → 诊断结论是"信息不全、不敢修" → **直接停下**。
更糟的是它给用户的建议是"**可能这个文件夹的所有者不是你**"——**实测所有者就是你本人**，这条建议是错的，照做没用。

### 4-2 【会误用】「Auto review」听起来更安全，**实际是把限制整个关掉**

它启用时的确认框里，产品**自己写了**：

> 「**Auto review 不使用沙箱。** ……每次操作前都会由**与当前 agent 相同的模型**进行审查；……此功能仍属实验性，**可能误放行或误拒绝**，并会消耗额外 token。」

翻译一下：
- 它**关掉了限制**（等于「完全权限」的放开程度）；
- 换来的是一层"AI 自己审自己"的检查（审查者和干活的**是同一个模型**）；
- 产品**自己承认可能误放行**。

**我实测确认了"误放行"**：我让它往**程序安装目录**（`…\Programs\tpt-work\`）写文件——这明显是可疑操作——**它直接写了，没拦、没问你**。

**结论**：这一档**不要当成"比默认档更安全"来用**。

### 4-3 【想要更强的隔离，拿不到】切换档位的界面**根本不存在**

产品里其实做了**两套**限制机制：
- **ACL 档**（当前在用）：就是上面说的"只限写"那套，装完即用；
- **提权档**（更强）：让 AI 用**另一个低权限账号**跑命令，隔离更彻底 —— 但需要**装一次**（要管理员授权）。

**问题是**：切换这两档的那个设置界面**不存在**。我把设置里 7 个页面全点了一遍、连隐藏元素都搜了，**找不到任何"受限执行 / 沙箱 / 提权"的入口**；而其代码和说明文档在包里是**齐全的**（说明"本应有"）。

**后果**：**提权档对用户不可达**，你只能用 ACL 档 —— 而它在普通文件夹上还会失败（见 4-1）。

## 五、两个小问题（提一下，别当大事）

| 问题 | 说明 |
| --- | --- |
| **`.git` 目录没保护** | 项目里 Git 的元数据（`.git` 文件夹）**可以被 AI 改写**。我实测改掉了 `.git/HEAD`，**成功了**（测完我改回来了）。一旦被误改，仓库可能就坏了 |
| **硬链接会"漏"到项目外** | 如果项目里存在**硬链接**文件（`pnpm` / `node_modules` 会大量使用）且指向**项目外**，那个外部文件会**被一起放开**——我第一轮测试就因此**真的删掉了项目外的一个文件** |

## 六、顺带确认的两件事（不算问题，但要知道）

| 项 | 说明 |
| --- | --- |
| **读取、联网、看进程列表 都不受限制** | 这是**设计如此**，产品界面上也**如实写了**（ACL 档的提示里明确写"它只限制写入——读文件、访问网络、枚举进程都不受限"）。所以别指望这一档能防止"信息被读走" |
| **测试给文件夹留了"永久标记"** | 只要是当过项目的文件夹，会被加上一处**清不掉的权限标记**（我手工清过，清不掉），且这个标记会让**同一台机器上其他低权限程序也能写这个文件夹**。规格里也承认了这一点 |

## 七、结论

> **限制功能本身是"对"的** —— 该拦的都拦住了、该允许的也允许，切换即时生效、确认框齐全，**我没找到能硬闯的漏洞**。
>
> **但它有三个"根本用不上"的问题：**
> 1. **普通文件夹直接跑不起来**（最要紧，见 4-1）；
> 2. **自带的诊断修复工具也救不了**，还给出**错误**的修复建议；
> 3. **更强的那一档你没有入口**（见 4-3）。
>
> **另外「Auto review」名不副实** —— 实际是关掉限制，且它的"审查"实测**没拦住可疑操作**。

### ⭐ 一句话判断：能不能用，**看你的项目放在哪个盘**

这是使用者最该记住的一条规律（也是 4-1 的根因）：

| 你的项目文件夹在哪 | 继承到的权限 | 结果 |
| --- | --- | --- |
| **用户目录下**（`C:\Users\你\…`） | 继承给该用户**完全控制** | ✅ **正常可用** |
| **数据盘上新建的**（`D:\`、`E:\`…） | 只继承到"**可修改**"，不含所需的高权限 | ❌ **一条命令都跑不了** |

**为什么能一眼判断**：代码里加那个"权限标记"需要**像"文件夹所有者"才有的高权限**；数据盘根下新建的文件夹，默认只给你"可修改"，所以标记加不上、整条链路就断了。

**换句话说**：
> **"其实还可以"要加一个前提 —— 项目别放在数据盘上。**
> 隔离逻辑本身没毛病，但**它有一个静默的前置条件**：文件夹权限必须够。用户不知道、产品不提示、出错了还修不了 —— 属于"**能跑通但不健壮**"，一旦踩中就掉到"完全不可用"。

### 日常怎么用（给使用者的建议）

| 场景 | 建议 |
| --- | --- |
| 绝大多数情况 | 就用默认的**「工作区内修改」**；**项目放在 `C:\Users\你的用户名\` 下面，别放在数据盘（`D:\`、`E:\`）** |
| 「完全权限」「Auto review」 | 只在**完全信任当前任务**时用；**不要**把 Auto review 当"更安全的默认档" |
| **如果 AI 一条命令都跑不了** | 大概率是 **4-1**：项目文件夹权限不够。**换到用户目录下的文件夹**，或请人给该文件夹**加一下"完全控制"权限**，即可恢复 |
| 需要"只读"场景 | 用「仅可查看」，实测有效 |
| 需要"只读"场景 | 用「仅可查看」，实测有效 |
| 想要更强隔离 | **目前拿不到**（4-3），需要产品先补上那个设置入口 |
