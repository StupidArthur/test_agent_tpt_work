# 03 指标与容量

## 指标口径

| 指标 | 计算与边界 |
|---|---|
| 成功率 | 通过对应场景全部必需断言的请求/轮次 ÷ 全部正式尝试；HTTP 200 不单独构成成功 |
| 端到端耗时 | 发起到完成、失败或超时。分别报成功样本和全部尝试的 n/mean/p50/p95 |
| 首事件等待 | 首个完整 SSE data 帧；可能是 role、心跳或元数据，不等于首正文 |
| 首正文/推理/工具等待 | 各类第一个有效增量，缺失记 null。内容类别分开，不互相替代 |
| 单请求输出吞吐 | 服务 usage 的 output/completion tokens ÷ 该请求端到端秒数；标明包含排队、网络、推理与输入处理 |
| 观察到的文本增量节奏 | 正文 delta 数与时间间隔，单位 chunks/s 或 ms；没有 tokenizer/服务 token 时序时不称 token 解码速度 |
| 阶段请求吞吐 | 正式发起/完成请求数 ÷ 正式阶段墙钟时间；两个计数都报，说明排空时间 |
| 用户轮次吞吐 | 成功完整业务轮次数 ÷ 正式阶段墙钟时间；工具轮次通常多于一个请求 |
| usage 完整率 | 有效计量样本 ÷ 完成样本；缺失为 null，不能填 0。总 token 与输入/输出需一致（按协议计量定义） |
| 错误分布 | 401/403、400/404/422、429、5xx、连接错误、超时、流内失败、无终态、内容/工具断言差异分别计数 |

p95 使用排序后最近秩 `ceil(0.95*n)`，与报告一并注明 n。小样本 p95 只反映这些样本，不是置信保证。不能拿 tok/s 除 chunks/s 推断“并行路由数”，也不能仅凭事件集中到达断定“伪流式”。

## 请求并发和用户并发

**请求并发**是同时在途的 HTTP 请求数。CAP-01 的 burst 扫描只能回答一次请求波次表现。

**同时活跃用户**在本设计中是闭环会话：每个用户按固定业务场景发送一轮，等整轮完成，再等待固定思考间隔，发下一轮。单用户同一时刻最多一个在途请求；工具轮次包含模型调用、工具结果回填和最终回答。

这不是登录人数、日活或安装量。用户等待期间没有在途请求，因此 N 用户不等于 N 持续请求。必须同时报告用户数、峰值/平均在途请求、轮次/s 和请求/s。

## 先定义工作负载

必须固定以下字段；换字段就是另一份容量结果：

1. 模型与可观测路由、思考档的真实 wire 参数、协议与流式选项。
2. 目标输入 token 档、实测 input usage、输出上限及实际输出分布。
3. 文本/工具场景、每轮请求数、工具执行时间（本地加法为近零，不代表真实外部工具耗时）。
4. 思考间隔、每用户请求串行规则、每轮历史构造方式。
5. 凭据方式：同一 key 压测还是多用户独立 key；账户/租户/模型限流。单 key 受限时只能给单 key 可见容量，不能外推整个平台。
6. 网络路径、测试机资源、客户端连接方式、超时与重试策略。

稳定曲线建议每轮重置为相同规模的固定历史，避免上下文不断增长干扰比较；另用 PERF-04 检查长上下文。若业务确需累积历史，单开该负载并记录增长，不能混入同一曲线。

模板建议建立两档：**短文本档**与**典型工具档**；上下文和输出规模由业务预期给出。未给出时可以测实验档，报告必须称实验档，不能称真实用户容量。

## SLO 是容量结论的前置

可讨论的示例：成功率 ≥99%、轮次 p95 ≤10s、首正文 p95 ≤2s。**这些数值不是已确认产品指标。** 必须在运行前固定真实 SLO；结果出来后不能调宽阈值凑通过。

有推理的模型可能先输出推理很久；正文首等待仍照实统计，另报首推理等待。工具场景首正文常在第二次请求，以整轮起点计时；首工具也单列。

容量档位达标需：样本/持续时间够、成功率够、成功轮次延迟达标、应有的首正文完整取得且达标。取值缺失或样本不够为“未能判断”，不是通过。失败轮次照计失败率，并保留等待时间，防止只看成功快请求。

## 分档及持续复核方法

### A. 试运行

单用户少量样本确认请求、断言、计量和失败记录都正确。确认客户端本身没有资源瓶颈，再开始正式负载。这里不产出最大用户数。

### B. 寻找边界

示例档位 `1, 5, 10, 20, 50, 100`，按已声明最大负载截断。每档暖机后，以同步起点执行闭环用户场景；正式阶段至少 **2 分钟且 30 轮次**，两条件都满足才结束发起，再排空已有请求。

设阶段最晚结束时间，避免永远等够成功样本：例如 10 分钟发起上限，轮次计的是全部尝试。到上限还不够样本时记测量不足；所有请求有超时。发起期间和排空期间分开计时。

按档位推进，遇到首个不达标档位记录边界；后续可按已安排队列补一个更细中间档，不要自动无限加压。若 20 不达标、50 却通过，标非单调并复核时段、配额、路由与客户端，不将 50 直接认作可靠容量。

### C. 复核可推荐负载

对候选最高达标档及首个不达标档，分别做 **至少两个独立窗口，每窗口 ≥10 分钟且 ≥100 轮次** 的持续复核。每窗口设明确最长发起时间（示例 30 分钟），并公开实际轮次；不够样本即未能确认。窗口间完成排空与低负载恢复检查。

报告逐分钟统计、首末窗口趋势、队列/在途数量、限流和错误；不能只报整个 10 分钟的平均值掩盖尾部恶化。配合 CAP-05 的开放到达确认闭环降速没有隐藏排队问题。

上述时长是本设计默认方法，可在执行前按预算另定。缩短后的结果称初筛，不能沿用持续复核结论。任务开始前估算请求数与时间；本设计没有“全套一定 5～8 分钟”的承诺。

## 开放到达与客户端瓶颈

闭环负载会因服务变慢而自动降速。因此 CAP-05 另按已声明轮次到达率调度，记录计划到达时间、实际发起时间和完成时间；排队等待纳入用户等待。设最大在途数与队列上限，达到上限记拒绝/未能发起，不能静默丢弃。

开放到达报告“在 X 轮次/s 下表现”，不直接改称 X 用户。监控压测机 CPU、内存、线程/连接、调度滞后和实际在途；若客户端到达率跟不上，结论是压测条件不足，不能判网关容量边界。

## 怎么写用户数结论

- 全部档位通过：“在负载 L、SLO S、测试凭据模式 K 下，已持续验证到 N 同时活跃用户；更高未测，最大值未知。”
- 有达标档 U 与失败档 F：“当前已验证 U 用户；F 用户未满足某项 SLO，边界位于已测档位之间，不能声称精确最大值为 U。”
- 只做请求 burst：“已测 N 同时在途请求；没有用户容量结论。”
- 无 SLO、样本不够、非单调或客户端受限：“有观测数据，尚不能确认可支持用户数。”

同时给出失败项、配置/模型/上下文边界、额度是否瓶颈，以及已测用户数是否经过持续复核。不要用经验比例把 API QPS 外推成注册用户数。
