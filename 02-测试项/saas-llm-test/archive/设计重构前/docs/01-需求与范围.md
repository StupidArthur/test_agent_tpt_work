# 01 需求与范围

## 需要回答的四个问题

| 编号 | 测试需求 | 合格结论需要什么 |
|---|---|---|
| R1 | 通用 LLM API 能不能正确调用 | 鉴权、请求/响应、流式结束、上下文和声明能力有真实断言 |
| R2 | 网关能不能供 TPT Work 的宿主适配器使用 | 对应包版本的 Responses 请求、事件、工具调用、历史和目录契约通过 |
| R3 | 服务表现如何 | 明确条件下的延迟分布、有效内容等待、吞吐、失败率与稳定性 |
| R4 | 支持多少同时活跃用户 | 定义用户负载、实测分档、SLO、持续复核和已测边界；不能用请求数代替用户数 |

## 范围边界

测试对象是测试机到网关、网关到上游共同形成的 API 服务。客户端测得的是这条路径的表现；没有分段计时或上游日志时，不能断言瓶颈来自网关、网络或模型某一层。

不测试软件界面、项目、技能/专家、记忆、附件管理、权限设置、账号体系或软件崩溃。工具调用用本地无副作用的加法函数；图片用固定图片夹具，二者都是 API 协议测试，不是软件操作。

不承诺全面评价模型智能。固定文本、指令、上下文、工具、图片小样本用于判断“服务能完成必需工作流”；若模型未按指令输出，记录真实差异，并与协议错误分别归因。不能由这些小样本推导总体智能排名。

## TPT Work 的契约依据

资料来源：[本地 llm-tpt 包 README](../../../01-产品资料/安装包技术资料/原始提取/dsh/node_modules/@tpt-work/llm-tpt/README.md)。这是历史安装包提取资料，执行前必须核对当前包是否沿用契约，记录版本及资料哈希。

该资料描述的默认 provider 使用 `openai-responses`：

- `GET /models` 获取模型；目录可为数组、`{data: [...]}` 或 `{models: [...]}`。
- `POST /responses`，Bearer 鉴权，`stream: true`。
- 用户文本为 `input_text`；系统指令进入 `instructions`；图片为 `input_image`。
- 输出约束用 `max_output_tokens`；工具是平铺的 Responses function 定义。
- 工具输出用 `function_call_output`，按 `call_id` 对应；工具参数保留原始 JSON 字符串。
- 思考档用 `reasoning.effort`；off 省略字段，不假定是字符串 `off`。
- 处理正文、推理、工具参数增量与完成/失败事件；没有终态的流不能算成功。

Chat Completions 可作为另一种通用接口单独评估，但它的成功不代替以上要求。软件内部重试、故障转移、默认模型配置不纳入此次测试；只检查网关提供的协议事实。

## 哪些是必测，哪些有条件

**TPT 基础可用必测**：当前所需的模型发现、鉴权、Responses 文本流、指令、历史、工具调用及输出回填、正常/异常终态、错误后的正常 API 请求。按当前实际业务声明决定图片和思考档是否必需。

**声明能力才测**：Chat 非流式/流式、JSON 模式、图片、多思考档、丰富目录字段。能力未声明不判失败；能力声称支持却不工作，记录差异。可选字段缺失不随意升级为目录缺陷。

**需要隔离条件**：可控制的 429、5xx、连接断开、慢响应、流内失败。无条件时保留未验证清单；普通成功请求无法覆盖这些项。

**性能与容量**：至少为主力模型、业务所需思考档和主力场景建立基线。模型/思考档先逐项做短可用性检查，再选择容量对象；不对每个未购买模型盲目发压力。

## 结论等级

1. **API 契约已验证**：只针对已测协议、模型、能力和包版本。
2. **目标负载达标**：对应负载、SLO、持续时间和样本都满足；单次请求通过不够。
3. **容量边界已测**：相邻达标/不达标档位经过持续复核。给范围，不编造精确最大值。
4. **仍需验证**：未声明能力、故障环境缺失、计量不足、版本不匹配、样本不足或 SLO 未定。

无论哪一级，都不写“软件端到端测试通过”。
