# 测试方案

目标：回答网关是否能正常供 TPT Work 使用、用户等待多久、失败概率多少、不同体验要求下可支持多少同时活跃用户。范围是 LLM API；软件 UI、账号体系和第三方工具服务不在本项。

## A 用户体验：正式报告先回答这些问题

|核心场景|回答的问题|主要观测|
|---|---|---|
|普通交互|多久开始有效回应、多久完成、会不会失败|TTFT、请求 E2E、有效请求成功率|
|标准 Agent|任务能否完成、首反馈与整个工作多久结束|任务成功率、任务 E2E p50/p95、首有效反馈 p50/p95|
|上下文增长|历史变长后多等多少|短/典型/长 TTFT 与 E2E、相对短上下文退化|
|用户容量|3/5/10 秒要求下能服务多少活跃用户|成功率≥99%且 E2E p95 分别达标的用户曲线|

## B 通用性能：解释体验

固定七项：Success Rate、TTFT、E2E Latency、Output tokens/s、Requests/s、Agent turns/s、Error Rate / Error Distribution。定义和体验映射见 [指标定义](06-指标定义.md)。请求与完整任务分表，不混总体通过率。

## C 兼容性 / 诊断 / 条件：保证可信与定位原因

[Compatibility Smoke](../cases/00-兼容性Smoke.md) 是生产配置的轻量前置；主报告只给能力小表。详细 API/TPT 断言保留，矩阵、故障注入和路径对照按 [触发规则](../cases/07-诊断与条件测试.md) 使用。

## 默认执行流程

1. 在探索任务冻结生产配置、负载、成功断言、安全上限与样本计划。
2. Compatibility Smoke：模型/鉴权/Responses/Streaming/History/Tool/Incomplete/失败后健康。
3. 普通短请求、长回答、短/典型/长上下文、标准 Agent 基线；共享正式样本，暖机单列。
4. 普通用户与标准 Agent 各自建立容量曲线；在关键边界复核、开放到达验证、排空恢复。
5. 用 [固定模板](../templates/报告模板.md) 报告 A、B；C 只展示兼容性小表与影响结论的问题。

兼容性前置失败时不能宣称相关核心路径可信；记录受影响范围。Agent 不调用指定工具降低任务成功率，但不自动变成网关协议失败，不自动禁止独立请求曲线。

核心新增门槛：必须写出“这个指标变差，TPT Work 用户具体感受到什么”。回答不出来就归 C，不进入默认队列。覆盖数不是体验、通过率或容量。
