# 02 测试方法

## 1. 实例与断言

测试项是规则，执行实例是具体的目标、协议、模型、思考档、样本和负载。实例编号例如 `TPT-06/gateway-a/model-x/low/sample-01`。每个实例写清预期，不能执行后按结果改预期。

用例状态使用：通过 / 失败 / 不确定 / 未验证。通过需所有必需断言取得实际值并满足；观测程序失效或读值有矛盾时为不确定，不能直接算产品失败。缺前置是未验证，记录缺失依赖和补测条件。

协议断言、内容断言、性能 SLO 分开记录。例如 HTTP 200 但工具参数不合法是契约/工作流差异；延迟超标是性能不达标；取值失败不是模型拒答。

## 2. 请求样本

- 文本探针：要求仅返回固定标记 `GW_CHECK_7c91`，严格比较正文 trim 后值；原始正文也保留。
- 上下文探针：第一轮给随机标记，第二轮不重复标记，带回真实历史，要求回忆。第二轮请求中答案只能存在于历史部分。
- 工具探针：强制调用 `add_numbers(a=17,b=25)`；本地验证并返回 `42`，第二轮仅返回工具结果。不要让 LLM 替代工具计算。
- 长输出：固定解释题目与输出上限。上限是最大允许生成量，不保证模型真的生成那么多；记实际 usage、结束原因和正文长度。
- 长上下文：固定长度填充并插入中部/尾部随机标记，问指定位置的标记；问句不带答案。保留完整 prompt 或独立夹具加哈希。
- 图片：本地确定的 PNG，预先写明问题与正确答案，记录文件哈希。避免网络图片和模糊视觉判据。

这些探针测工作流可用性。遇模型内容偏差先核对请求、返回和工具参数，区别内容不服从、协议不合法和观测错误；保留候选差异待审。

## 3. SSE 与结束

按 SSE 帧解析，而不是每个 TCP 块当一个事件。处理 CRLF、空行分帧、注释、多个 `data:` 行、跨块 UTF-8、未知事件和 JSON 解析失败。原始字节/帧与解析输出同时留证。

- Chat：role/空 delta 不算首正文。工具增量按 index/id 聚合；检查 finish_reason 与结束标记。`stream_options.include_usage` 若声明支持，验证末尾 usage 帧；没有 usage 仍可能完成，但不能虚构 token 指标。
- Responses：区别 `response.output_text.delta`、推理 delta、工具参数 delta；按 item id/output index 关联；正常完成需成功终态。错误、失败、未完成或 EOF 没有终态不得判成功。
- 对 delta 拼接值与最终值都存在的响应，检查一致性。不得用最终内容覆盖错误增量后声称流式通过。
- 正常未知/心跳事件不直接当失败；带错误的未知数据不能静默丢弃。以对应版本的适配器契约为准。

流内错误和半途断开的错误处理使用隔离目标，不能由成功流推断。具体事件依据见 [来源](05-来源与历史.md)。

## 4. 计时与样本

使用单调时钟。从发起请求前开始到读到终态/失败并关闭响应结束。分别记录响应头、首完整事件、首推理、首正文、首工具事件和完成时间。

性能测量不隐藏重试。若业务确有重试，另建“含重试用户等待”场景，记录每次 attempt；不能将重试后的成功覆盖首失败。

warmup 与正式样本分开。每个样本，无论成功、超时、错误或未完成，都进入请求总数和错误率。仅成功样本的延迟分布必须标明是条件分布，同时提供所有尝试的等待时间与失败分布。

短基线建议正式 30 次，长输出/上下文每档 10 次；这些是默认设计，不代表足以证明极高分位或生产可靠性。样本量、实际持续时间必须公开。

## 5. 共享场景与差异复核

同一个 Responses 工具调用往返可以支撑 API-06、TPT-04 和 TPT-07 的相应断言：引用同一证据，分别给断言值。不要为每个编号重跑完全相同场景。性能样本需正式计时口径，不能随意拼接功能测试样本。

发现异常先核对：目标/模型/档位 → 发出的 wire 请求 → HTTP 与 SSE → 实际内容 → 断言。观测代码有误可有限修正，再保留原 attempt 与新 attempt。产品差异不在本轮偷偷改预期。

## 6. 多目标比较

保存协议、模型、实际路由、完整请求参数、prompt 哈希、代码版本、网络和时间。比较前检查工作负载是否一致，注明不能对齐的部分。同名 `low` 不证明计算量相同；跨模型结果属于服务表现对照，不能直接推导网关开销。

公网/内网对比尽量使用同模型同参数、交错测量或同时间窗口；若未控制路由和网络变化，差值只作观察，不解释成某一层耗时。旧版结果独立展示，不与新口径直接合并。
