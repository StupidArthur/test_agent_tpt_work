# 容量与用户模型

[指标定义](06-指标定义.md) 是计算依据。容量问题是“不同体验要求下能支持多少同时活跃用户”，不是只找最大请求并发。

## 固定判据与输出

普通用户与标准 Agent **分别**建表，负载不能互相换算。每档同时要求有效请求/任务 success_rate ≥99%，并分别评 E2E p95≤3s、≤5s、≤10s。不要求产品先拍板唯一 SLO；这些是本项目三条评价线，不是行业强制标准。

|用户体验要求|已验证同时活跃用户|首个不满足档位|规划总用户|
|---|---:|---:|---:|
|E2E p95≤3s|N3|F3|N3×5|
|E2E p95≤5s|N5|F5|N5×5|
|E2E p95≤10s|N10|F10|N10×5|

规划总用户=同时活跃用户×5 是当前产品规划换算，**不是五倍用户一定同时在线，也不是实测注册容量**。无已验证档写“尚无/未知”，不要填 0 冒充结果。Agent 单用户已超过某阈值可写“已测1人不达标”；其他阈值仍可测，任务质量失败与协议失败分别解释。

## 用户、请求与负载

闭环 U 用户：每人一个完整 turn，完成或失败后等待固定 think time 再开始；轮内可有多个顺序 LLM 请求。记录 U、任务在途、真实请求在途、think time、凭据/配额模式、上下文/输出、工具等待和历史策略。[标准 Agent](07-标准Agent负载.md) 保留真实系统/工具上下文。

请求 burst 和连接池排队只说明请求压力，不得把启动协程数填写为活跃用户；单 key 只能解释该凭据/共享配额场景。吞吐/每用户频率换算可作为估计，但必须标估计，不代替直接闭环用户验证。

## 容量实验流程

1. 冻结生产配置、有效答案/任务断言、三阈值、成功率、用户档位、思考间隔、窗口/最小样本、最高用户/请求/连接/队列、费用与时间预算、停止条件。网关和客户端均要可承受。
2. 健康单用户测量，识别空答案、截断、夹具或客户端问题。重大前置故障先修复；仅3秒不达标不阻止找5/10秒边界。Agent 质量失败单列，独立请求曲线仍可继续；质量不达标不能宣称任务用户容量达标。
3. 分档提高 U，逐档输出成功率、TTFT p95、E2E p95、Requests/s、Agent turns/s及实际在途。初筛默认每档至少2分钟且30完整尝试；实际预算允许的样本计划在任务冻结。样本不足为未验证。
4. 对每条阈值找相邻最高通过/首次不通过档，在间隔内细分。继续到三条边界明确或安全上限；安全上限处仍通过只给已测下界，首失败未知。非单调结果有限复核，不能挑偶然高档当最大容量。
5. 只复核关键候选通过档和首失败档，共用不同阈值重合的窗口：默认每档两个独立窗口，每窗≥10分钟且≥100尝试。任务可提高样本要求；不能看结果后缩短或补改判据。记录逐分钟趋势、样本不确定性和客户端资源。无法安全复跑失败档说明限制。
6. 用开放到达复核候选边界，检查闭环因响应变慢自动减压而掩盖排队；最后停止发起、排空并低负载健康检查。边界持续复核与排队验证未完成时只报初筛，不报已验证生产容量。

## 开放到达与恢复

预定任务到达率独立于响应速度；在候选吞吐附近冻结低/目标/高档、队列与在途上限，至少2分钟且30计划到达。记录计划到达、实际发起、结束、未发起/拒绝，全部对账；用户等待从计划到达计。跟不上到达率、连接池限流或客户端积压不能默认为服务端排队。

开放到达是容量结论的验证方法，不是独立管理 KPI。发生持续积压时收窄闭环容量的适用性，保留实际曲线。

恢复是实验完整性检查：排空期限、停止残留、至少10个低负载健康 turn、与原基线的延迟容差在计划冻结；异常不声称恢复。主报告只简述，详细过程进附件。

## 计算和执行边界

容量 p95 用全部完成/失败尝试的 E2E，成功率门槛同时约束快速失败；TTFT 缺失率单列。预算耗尽、客户端受限、未排空或未知值不构成网关失败边界。

现有 capacity_suite 只评一套 SLO，提供文本/简化工具闭环、持续窗口、恢复。它**未自动实现三阈值汇总，也未内置标准 Agent workload**。执行任务须复用它的原始样本离线分别评3/5/10秒，或登记复用的 Agent 回放驱动；不可把单阈值自动结论当新方案全覆盖。旧 JSON 执行计划仍需填已确认的执行参数与授权；三条分析线不等于允许发请求。
