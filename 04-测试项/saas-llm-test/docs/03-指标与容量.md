# 容量与用户模型

[指标定义](06-指标定义.md) 是计算依据。容量问题不是单纯寻找“最大并发”，而是回答：**在不同体验要求下，网关服务和 TPT Work Agent 分别能支持多少同时活跃使用者。**

## 两类容量必须分开

### 1. 网关服务容量

代表普通 LLM API 请求的服务承载能力。

判据：

- Gateway Service Success Rate ≥99%；
- 分别评价请求 E2E p95 ≤3s、≤5s、≤10s；
- 模型仅因标点、固定 marker 的严格字符不一致等内容遵循问题，不自动算网关服务失败；
- 空正文、异常截断、HTTP/传输/协议失败、无合法终态仍属于网关服务失败。

该结果回答：

> 在冻结的简单/典型请求负载下，网关服务在 3/5/10 秒体验要求下能承载多少同时活跃请求用户。

### 2. TPT Work Agent 用户体验容量

代表 [标准 Agent workload](07-标准Agent负载.md) 下完整任务体验。

判据：

- Agent Task Success Rate ≥99%；
- 分别评价完整 Agent task E2E p95 ≤3s、≤5s、≤10s；
- 工具没有按要求调用、工具往返错误、最终业务断言失败都会使 Agent task 失败；
- 同时保留 Protocol/Gateway Service 层成功率，以区分“网关不可用”和“Agent/模型任务质量失败”。

该结果回答：

> 在冻结的 TPT Work 标准 Agent 负载下，3/5/10 秒体验要求分别能支持多少同时活跃 Agent 用户。

两类容量不能互相替代。短 OK/marker 请求的高容量不能外推成真实 Agent 用户容量。

## 固定容量输出

网关服务与标准 Agent 各自生成一张表：

|用户体验要求|已验证同时活跃用户|首个不满足档位|边界|规划总用户|
|---|---:|---:|---|---:|
|E2E p95≤3s|N3|F3|N3～F3|N3×5|
|E2E p95≤5s|N5|F5|N5～F5|N5×5|
|E2E p95≤10s|N10|F10|N10～F10|N10×5|

规划总用户=同时活跃用户×5 是当前产品规划换算，**不是五倍用户一定同时在线，也不是实测注册容量**。无已验证档写“尚无/未知”，不要填 0 冒充结果。

本项目不要求产品预先拍板唯一 3/5/10 秒 SLO；测试必须给出三条体验线，业务可据此选择服务档位。成功率门槛和三条延迟线必须在运行前冻结，不得看结果后修改。

## 用户、请求与负载

闭环 U 用户：每人一个完整 turn，完成或失败后等待固定 think time 再开始；轮内可有多个顺序 LLM 请求。记录 U、任务在途、真实请求在途、think time、凭据/配额模式、上下文/输出、工具等待和历史策略。

请求 burst 和连接池排队只说明请求压力，不得把启动协程数直接填写为 Agent 活跃用户；单 key 只能解释该凭据/共享配额场景。吞吐/每用户频率换算可以用于规划估计，但必须标为估计，不代替直接用户验证。

## 容量实验流程

1. **冻结配置**：生产模型、reasoning、协议、负载、成功定义、3/5/10 秒阈值、成功率、用户档位、think time、窗口/最小样本、最高用户/请求/连接/队列、费用预算和停止条件。
2. **健康基线**：先跑单用户，识别空答案、截断、夹具或客户端问题。单用户只是不满足 3 秒时，不阻止继续寻找 5/10 秒边界。Agent 质量失败单列；网关服务曲线仍可继续，但 Agent 任务质量不达标时不能宣称 Agent 用户容量达标。
3. **分档扫描**：逐档提高 U，输出对应成功率、TTFT p95、E2E p95、Requests/s、Agent turns/s和实际在途。初筛默认每档至少 2 分钟且 30 次完整尝试；任务可按成本另行冻结更高样本。
4. **寻找边界**：分别找 3/5/10 秒三条线的最高通过档和首个不通过档，在间隔内细分。继续到三条边界明确或达到安全上限。安全上限仍通过只给下界。
5. **边界复核**：只对关键候选通过档和首失败档持续复核，可共用三条阈值重合的窗口。默认每档两个独立窗口，每窗≥10分钟且≥100尝试。记录逐分钟趋势、客户端资源和样本不确定性。
6. **开放到达验证**：在候选吞吐附近用预定到达率检查闭环因响应变慢自动减压而掩盖排队的问题。
7. **恢复**：停止发起、排空并执行低负载健康检查。恢复只是实验完整性，不单列管理 KPI。

## 非单调与客户端限制

容量曲线可能因模型调度、网络、缓存、客户端连接能力出现非单调结果。出现“更高档反而明显更快/更成功”时必须有限复核，不可挑偶然高档作为容量。

计划并发必须同时报告实际峰值在途和客户端启动跨度。连接池、socket、线程、CPU或调度器限制使实际压力未送达时，结论是“客户端条件不足”，不是网关容量失败。

HTTP 500/503、429、no_http_status、ClientConnectorError 等必须分开统计；没有服务端日志时不能把客户端连接错误定性为网关内部根因。

## 开放到达与恢复

预定任务到达率独立于响应速度；在候选吞吐附近冻结低/目标/高档、队列与在途上限，至少 2 分钟且 30 个计划到达。记录计划到达、实际发起、结束、未发起/拒绝，全部对账；用户等待从计划到达计。

开放到达是容量结论的验证方法，不是独立管理 KPI。发生持续积压时，要收窄闭环容量结论。

恢复检查至少包含：排空期限、停止残留、低负载健康 turn 和相对基线的延迟变化。异常时不声称已恢复。

## 计算与执行边界

容量 E2E p95 使用全部已完成请求/任务的实际耗时；失败率由相应成功率门槛单独约束，失败不能作为零延迟。TTFT 缺失率单列。预算耗尽、客户端受限、未排空或未知值不构成网关失败边界。

现有 capacity_suite 只评一套 SLO，提供文本/简化工具闭环、持续窗口和恢复。它**未自动实现三阈值汇总，也未内置标准 Agent workload**。执行任务须复用原始样本离线分别评价 3/5/10 秒，或登记复用的 Agent 回放驱动；不可把单阈值自动结论当作新方案全覆盖。
