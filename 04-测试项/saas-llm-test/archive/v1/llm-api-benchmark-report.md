# LLM API 性能对比测试报告

**日期**：2026-09-24
**测试方**：单机（Windows，公司网络）直连，Python 标准库 HTTPS
**对象**：
- **A**：自建网关 `flash` 模型 — `https://tpt.supcon.com/tpt-work-router/v1`（OpenAI 兼容，服务名 `ai-router`）
- **B**：DeepSeek 官方 `deepseek-chat` — `https://api.deepseek.com/v1`

> 注：DeepSeek 无 `flash` 型号，以其默认快模型 `deepseek-chat` 对标；另测 `deepseek-reasoner` 对标高思考档位。

## 3. 核心结果

### 3.1 延迟

| 指标 | flash 网关 | deepseek-chat | 差距 |
|---|---|---|---|
| 短请求非流式 均值 | 1176 ms | **860 ms** | DS 快 27% |
| 短请求 p50 / p95 | 1190 / 1436 ms | **796 / 1367 ms** | p50 快 33% |
| **流式 TTFT 均值** | **1509 ms** | **210 ms** | **DS 快 7 倍** |
| TTFT p50 / p95 | 1533 / 1724 ms | 201 / 273 ms | |

### 3.2 吞吐

| 指标 | flash 网关 | deepseek-chat | 差距 |
|---|---|---|---|
| 1500 字端到端测试 | 135 tok/s | 141 tok/s | 表面持平* |
| **稳态解码速率（中段实测）** | **138.8 chunk/s** | **175.1 chunk/s** | **DS 快 26%** |
| 非流式长输出 | 134.4 tok/s | 163.8 tok/s | DS 快 22% |

\* 端到端短文本口径混入了 TTFT 与排队时间，掩盖了真实解码差距——即"没打满"的那部分。

### 3.3 并发扫描（每请求 800 tokens，N=1~100）

**flash 网关**

| 并发 | 聚合吞吐 | 单请求均延迟 | 成功率 |
|---|---|---|---|
| 1 | 129 tok/s | 6184 ms | 1/1 |
| 5 | 561 tok/s | 6769 ms | 5/5 |
| 10 | 995 tok/s | 8000 ms | 10/10 |
| 20 | 1688 tok/s | 9453 ms | 20/20 |
| 50 | 2126 tok/s | 12601 ms | 50/50 |
| 100 | **2212 tok/s（饱和）** | **19505 ms** | 100/100 |

**deepseek-chat**

| 并发 | 聚合吞吐 | 单请求均延迟 | 成功率 |
|---|---|---|---|
| 1 | 153 tok/s | 5219 ms | 1/1 |
| 5 | 685 tok/s | 5607 ms | 5/5 |
| 10 | 1342 tok/s | 5740 ms | 10/10 |
| 20 | 2646 tok/s | 5715 ms | 20/20 |
| 50 | 6001 tok/s | 5833 ms | 50/50 |
| 100 | **12538 tok/s** | **5765 ms** | 100/100 |

**解读**：
- **flash 容量天花板 ≈ 2200 tok/s，已在本测试中打满**：N=50→100 吞吐仅 +4%（2126→2212），延迟 +55%（12.6s→19.5s）——饱和曲线，**拐点位于 N=20~50 之间，N≈50 完全饱和**。
- **有效并行流估算**：flash 聚合上限 2212 ÷ 单流 139 tok/s ≈ **~16 路真并行解码**，暗示上游模型副本/网关转发池约在 16 量级，其余并发全在排队；DS 在 N=100 时 12538 ÷ 167 ≈ **~75 路**，约 flash 的 5 倍。
- **延迟退化模式不同**：DS 从 N=1 到 N=100 单请求延迟始终 ~5.7s（完全平推，到 100 仍未见拐点）；flash 从 6.2s 一路膨胀到 19.5s。
- 全部档位累计 335 个请求 **0 错误、无 429**——限流不是约束，纯容量问题。

### 3.4 长上下文与预填充

| 场景 | flash 网关 | deepseek-chat |
|---|---|---|
| 31K tokens 首次 | 4640 ms | 1451 ms |
| 31K tokens 原文重发 | **1055~1575 ms（命中缓存）** | 961~1127 ms（同样有缓存） |
| 60K 全新文本 ×3 | **7142 / 7138 / 7195 ms** | **1804 / 1744 / 1548 ms** |
| 60K 答案正确性 | ✅ | ✅ |

- 两边 `prompt_tokens` 口径一致（60015），可比。
- 全新文本预填充：flash ≈ **8.4K tok/s**，DS ≈ **35K tok/s** —— **DS 快 4 倍**。
- 两边均有前缀缓存，重复长前缀场景延迟都可降到 1~1.5s。

### 3.5 流式行为

| 行为 | flash 网关 | deepseek-chat |
|---|---|---|
| **短回答（~20 chunk）** | ❌ **攒批发**：22 个 chunk 同一瞬间（689ms）全部到达 | ✅ 真增量：首 chunk 200ms，跨度 908ms |
| **长回答（3000 字级）** | ✅ 真增量：首字 2109ms，中段稳定 ~152 chunk/s | ✅ 真增量：首字 198ms，~131 chunk/s |

> 做流式 UI 时，flash 网关必须能处理"短响应一堆 chunk 同时到达"的情况；打字机体验上 DS 首字快约 10 倍。

### 3.6 思考档位开销

**flash（同一问题 ×3）**

| 档位 | 平均延迟 | 平均输出 tokens |
|---|---|---|
| off | 1099 ms | 123 |
| low | 1315 ms | 153 |
| medium | 1384 ms | 164 |
| high | 1397 ms | 165 |

**DeepSeek（对标）**

| 模型 | 平均延迟 | 输出 tokens | 其中 reasoning |
|---|---|---|---|
| deepseek-chat | 752 ms | 3 | — |
| deepseek-reasoner | 1223 ms | 134 | 130 |

- 开思考的代价两边类似：flash +300ms，DS reasoner +470ms。
- ⚠️ flash `off` 档单次问题也输出 123 tokens，疑似思维链仍计入 `completion_tokens`（或 off 未完全关闭）。
- ⚠️ `max_tokens` 过小时（如 20），思考会吃光预算导致 **content 为空**——默认档位下务必给足 token 或显式 `think_level: off`。

## 4. 结论

**flash 网关的优势**
1. **稳定性**：全流程 100+ 请求 **0 失败**，无 429/5xx，p95/p50 ≈ 1.2，延迟波动小。
2. **功能完整**：OpenAI 兼容、双认证头、流式、思考档位、前缀缓存、图片输入（pro）俱全。
3. **并发可用**：累计 335 个请求覆盖 N=1~100，**全部成功、无限流封禁**；N=100 后仅表现为排队延迟而非报错（优雅降级，不熔断）。

**与 DeepSeek 的差距（按严重度排序）**

| 优先级 | 问题 | 量化差距 |
|---|---|---|
| 🔴 P0 | **流式首字延迟 TTFT** | 1509ms vs 210ms，**慢 7 倍** |
| 🔴 P0 | **短响应流式假增量**（攒批冲刷） | DS 短响应也逐步下发，flash 一次性到达 |
| 🔴 P0 | **并发容量已打满** | 天花板 ≈2200 tok/s（有效并行仅 ~16 路）；DS 到 N=100 仍线性增长至 12538 tok/s（~75 路），**差 5.7 倍** |
| 🟠 P1 | **长文本预填充** | 60K 全新 tokens：7.1s vs 1.7s，**慢 4 倍** |
| 🟡 P2 | 单流稳态解码 | 139 vs 175 chunk/s，慢 26% |
| 🟡 P2 | `think_level: off` 疑似未完全关闭思考 | 额外消耗 tokens |

**归因推测**：TTFT（7×）与预填充（4×）的差距远大于解码差距（26%），若网关后端接的是同级模型，瓶颈大概率在**网关/代理层的排队与缓冲逻辑**（nginx `proxy_buffering`、转发池排队）而非模型本身；短响应攒批现象也指向同一处。

**建议**：
1. 排查网关 SSE 缓冲配置（`proxy_buffering off` / 分块即时转发），优先解决假流式与 TTFT；
2. 容量方面已定位瓶颈：**有效并行仅 ~16 路**，需扩容上游模型副本/网关转发池（对照 DS 同场景 ~75 路）；建议按目标 QPS × 平均延迟（Little's Law）核算所需并行度；
3. 延迟敏感场景默认 `think_level: off` 并给足 `max_tokens`；
4. 长 system prompt / 知识库前缀利用好已验证存在的前缀缓存（重复前缀可省 3~4s）。

## 5. 测试局限

- 单一网络位置、单时段，未跨区域/跨运营商交叉验证；
- 样本量较小（延迟项每档 3~10 次），p95 参考意义有限；
- 并发扫描为单波突发（single burst），未做阶梯式加压与持续压测（soak），N=50 之后的"饱和"结论基于两档采样；
- 未测 `pro` / `deepseek-reasoner` 的完整矩阵，未测超长输出（>32K）与真实业务流量分布；
- token 计数以各 API 返回的 `usage` 为准，未做跨 tokenizer 折算核验。
