# TPT 网关短请求并发测试记录与报告

状态：实测记录已整理，结论待审。本文合并执行记录和结果分析；未重新发起请求。

## 1. 结论

本次测试中，100、200、400、800 请求并发启动的批次全部完整返回；1600 请求批次首次出现异常：1285 个完整返回、127 个 HTTP 500、1 个 HTTP 503、187 个客户端连接失败。未观察到 HTTP 429。停止升档后，单请求恢复检查成功。

随批次增大，成功请求平均响应时间从 100 档的 1.898 秒上升至 800 档的 15.084 秒。800 档虽然无失败，P95 已达 28.156 秒，因此“无报错”不能直接理解成满足交互性能要求。

**不能据此宣布网关最大并发为 800 或 1600。** 这是有限档位的一轮测试，未做稳定性重复验证；1600 档客户端“已发送但未结束”峰值为 955，服务端内部执行/排队数量没有取得。500/503 证明本轮确实收到了服务端错误，但根因尚未确认。

## 3. 执行记录与判据

1. 先取得单并发基线：顺序发送 10 个短请求，每次独立连接，无预热排除、无重试。
2. 本轮从 100 开始，按 100 → 200 → 400 → 800 → 1600 升档；各档创建并发请求、正常读取响应，全部收尾后才进入下一档。
3. 完整成功要求 HTTP 200、SSE `[DONE]`、存在 finish_reason，且没有流内错误或读取异常。`OK.` 与 `OK` 的文字差异保留，不因句号差异将完整接口响应计为性能失败。
4. 1600 档出现异常后停止升档，原计划的 2501 档未执行；没有重试失败请求。等待后仅做一次单请求恢复检查。
5. 本轮请求 3101 次（3100 个升档请求 + 1 个恢复请求），完整返回 2786 次。单并发基线 10 次单独统计，不混入升档成功率。
6. 客户端会话已关闭；未操作 TPT Work UI，未改设置。无法仅凭客户端关闭确认服务端内部任务已经终止。

## 4. 单并发基线

10/10 个 HTTP 200 且完整返回；6 次正文为 `OK`，4 次为 `OK.`。性能统计包含全部 10 次，原严格文字匹配断言及失败记录保留。

|指标|平均|P50|P95|最小|最大|
|---|---:|---:|---:|---:|---:|
|首正文响应|0.339 秒|0.296 秒|0.609 秒|0.265 秒|0.609 秒|
|完整响应|0.339 秒|0.296 秒|0.609 秒|0.265 秒|0.609 秒|

首正文与完整响应在本轮记录精度下相同，正文帧集中到达，不能解释为模型内部首 token 生成耗时。10 样本 P95 使用最近秩，等于最大值。基线采样客户端使用公共 `llm_probe`，升档使用 aiohttp，客户端实现不同，所以比较的是当次调用路径体验，不是严格隔离的网关耗时差。

## 6. 首次异常：1600 档

|类别|数量|证据与结论|
|---|---:|---|
|完整 HTTP 200|1285|完整成功率 80.31%|
|HTTP 500|127|响应正文为 nginx/1.14.1 通用错误页，具体根因未确认|
|HTTP 503|1|明确返回 `channel_error` / `no available channels`|
|未取得 HTTP 状态|187|客户端 `ClientConnectorError`，不并入服务端 500/503|

HTTP 500 原文的关键行：

```text
<head><title>500 Internal Server Error</title></head>
<center><h1>500 Internal Server Error</h1></center>
<hr><center>nginx/1.14.1</center>
```

HTTP 503 完整错误正文：

```json
{"error":{"code":null,"message":"当前模型暂时不可用: no available channels","param":null,"type":"channel_error"}}
```

187 个连接异常中，185 个提示“信号灯超时时间已到”、1 个提示“远程计算机拒绝网络连接”、1 个错误附加信息为 `[None]`。这些错误可能涉及本机、网络或远端连接资源，没有日志支撑时不定性为网关代码缺陷。

目前没有证据将 nginx 500 或 channel_error 归因为 DeepSeek 的余额限流或官方 2500 上限；本轮未收到 429，也没有取得上游并发计数。

## 7. 限制与后续处理建议

- 不将这一轮短请求结果外推为典型 Agent 用户容量，也不将“批次全成功”作为稳定性能达标结论。
- 若需要定位错误原因，优先对照该时间窗口的网关 nginx、路由服务与通道日志，检查 500 对应 upstream/连接错误及 503 对应通道状态；保留客户端连接失败的独立分类。
- 若要精确定位报错边界，需要先核验压测机连接能力，再在成功档位与首次异常档位之间补档并重复验证，同时采集服务端实际活跃请求/排队数。本轮未执行这些补测。
- 没有约定延迟 SLO，本报告只提供响应时间与错误事实，不给出“可支持多少用户”的结论。
