## 范围与方法

- 档位：`55 / 60 / 80 / 85 / 200 / 210`（初筛候选 55/80/200，首失败 60/85/210）。
- 每档 2 个独立窗口，每窗 `>= 600s` 且 `>= 100` 次实际尝试。
- 负载复用 todo_2：Responses API / `flash` / `reasoning.effort=low` / 流式 / `max_output_tokens=256` / 单 key / 简单唯一 marker `CAP_<12hex>`。
- 执行模型：U 个线程 barrier 同步发起一波 → 等该波全部结束 → think time 5s → 下一波；窗口之间执行 10 次低负载健康检查 + 30s 冷却。
- 成功分层：`gateway_service_success = protocol ok AND terminal=completed AND 非空正文`；marker 未严格逐字符回显记 `model_quality_mismatch`，不算网关失败。
- 安全停止：窗口内 429/5xx/timeout/connection_error 占比 `>5%` 时停止该窗口。

## 判据（原 README 4.4）

某档对某条体验线“持续验证通过”，必须**两个独立窗口都**满足：

```
Gateway Service Success Rate >= 99%  AND  E2E p95 <= 阈值
55/60 -> 3s ; 80/85 -> 5s ; 200/210 -> 10s
```

- 候选通过档反而失败 → 不自动扩大测试，允许该档再补 1 个复核窗口，保留原结果，报告“初筛与持续窗口不一致”。
- 候选失败档反而两窗都通过 → 边界未确认，最多增加一个相邻/中间档位再判断。

## 客户端有效性（原 README 4.5）

每窗采集 CPU / RSS / 线程 / TCP 连接数 / `actual_peak_in_flight` / `launch_spread`。
若某窗 `actual_peak_in_flight < planned * 0.90` 或明显客户端瓶颈，则该窗标 `client_limited=true`，不用于网关容量结论。

> 说明：本执行器对 TCP 连接数采用“每波结束后采样”，主要客户端有效性依据是 `min_peak_ratio`（每波峰值在途/计划）与 CPU/线程/RSS。

## 本轮结论（待审）

判据：某档对某体验线“持续通过” = 该档全部有效窗口均 `成功率>=99%` 且 `E2E p95<=阈值` 且无窗口 `client_limited`。

| 体验线 | 初筛通过/首失败 | 持续通过档 | 持续首失败档 | 与初筛一致 | ×5 规划总用户 |
|---|---:|---:|---:|---|---:|
| p95≤3s | 55 / 60 | **60** | **70** | 否 | 300 |
| p95≤5s | 80 / 85 | **85** | **100** | 否 | 425 |
| p95≤10s | 200 / 210 | **100** | **200** | 否 | 500 |

- 三条体验线的持续边界均**高于**初筛：初筛 55/80/200 偏保守。
- 3s、5s：60、85 两窗均通过；相邻档 70、100 两窗均不过（边界清楚）。
- 10s：**受客户端受限污染**。200 的三窗中 win1（峰值比 0.72）、win3（0.31）受限，win2/win3 成功率 98.83%/98.48%<99%；210 两窗 E2E p95 11.0/12.73s>10s。故 10s 通过档只到已实测的 100，200 为首个失败档，但 **200 的失败不能干净归因为网关内部问题**（见下）。
- 全程无 429、无 5xx、无 timeout；失败为 `incomplete`、少量 `connection/protocol`，以及不计网关失败的模型 marker `mismatch`。
- 200/210 档客户端受限证据：峰值比最低 0.31/0.33，单波 `launch_spread` 最大 9.28s，`connection` 错误集中在个别波 → 单进程多线程客户端在本机无法可靠产生 200–210 并发，相关窗口按 4.5 标 `client_limited`，不作为网关容量结论。
