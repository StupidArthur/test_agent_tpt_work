# todo_2 容量-延迟曲线补测（待审）

目标：在 Responses API / `flash` / `reasoning.effort=low` / **单 key** 下，给出不同响应时间要求（p95 ≤3/5/10s）对应的**同时活跃用户数**，并按产品口径 `总用户 = 同时活跃用户 ×5` 换算。

## 不变式

- 协议 Responses API；模型 `flash`；思考档 `low`；流式；`max_output_tokens=256`。
- `credential_mode = single key`，凭据 `flash-public-low`（沿用测试凭据；本轮使用 low，并非生产配置推断）。
- 每个正式请求保存机器可读原始证据（request / status / SSE 帧 / normalized / 时间点 / SHA-256）。
- 失败不重试、不覆盖；重复样本另存。某档失败不停止整任务，除非触发安全停止条件。
- 每 wave barrier 同步发起，尽量 100ms 内发起；`actual_peak_in_flight < planned×90%` 视为该 wave 无效（客户端瓶颈）。

## 判定

某档“可支持”需同时满足 `成功率 ≥ 99%` 且 `E2E p95 ≤ 阈值`。E2E 分位只统计成功 turn。

## 安全停止

1. 连续两档 p95>10s；2. 某档成功率<95%；3. 某档 (429+5xx+timeout)>5%；4. `actual_peak_in_flight<planned×90%` 且确认客户端瓶颈；5. 达到 1000 并发。触发后只在安全区间补边界。

| 延迟要求 | 已验证同时活跃 Agent | 首个不满足 | ×5 |
|---|---:|---:|---:|

### 关键说明
- **严格口径下简单文本边界恒为 20**：不是延迟限制，而是模型对随机 marker 有约 1% 的“未按要求回显”（把随机码当未知标识符解释），且与并发不相关（50→500 档约 0.9%~1.5%）。工具 turn 指令明确，成功率 100%，故严格=延迟口径。
- 215/250 档有 wave 的 `actual_peak_in_flight` 低于计划（0.69/0.53），该 wave 视为无效；已在曲线“峰值比”列出。它们高于已确定边界，不影响结论。
- 90/100、60/75 出现非单调，已用 4~6 wave 复测并合并；60 档复测后稳定 <10s。
- 全程无 429、无 5xx、无连接错误；失败仅 `content_mismatch` 与少量 `incomplete`。
- 未测更高档（安全停止于文本 300/500、工具 200），**不代表最大容量**。
