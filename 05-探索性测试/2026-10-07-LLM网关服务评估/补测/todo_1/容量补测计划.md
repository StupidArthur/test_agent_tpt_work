# 容量补测计划（todo_1 / T10）

本计划**不在本轮执行**；列出可执行步骤与**待管理者确认的参数**。未确认项不得当作已批准。依据 `04-测试项/saas-llm-test/docs/03-指标与容量.md`。

## 0. 现状与保留

- 已有观测（保留，不当作持续容量）：CAP-01 在途 1/5/10×3 波全通过；CAP-02 闭环 1/5 用户各 60s（26/125 轮，成功率 100%）；CAP-05 1 轮次/s×60s。
- CAP-02 的 **60 秒实验窗口短于设计默认（≥2min 且 ≥30 轮次）**，只能称初筛，不能称持续容量验证。

## 1. 统计与成功口径（先冻结，再跑）

- 成功率 = 通过全部必需断言的**轮次** ÷ 全部正式尝试轮次；工具轮含“模型调用→工具结果回填→最终回答”，任一步失败即整轮失败。
- 延迟 p95 用排序后最近秩 `ceil(0.95*n)`；同时报 n、mean、p50。失败轮次照计失败率并保留等待时间。
- 首正文以**整轮起点**计时；工具场景首正文常在第二轮。
- `usage` 缺失记 null，不填 0。并发请求数不改称用户数。
- 正式样本：单用户同一时刻 ≤1 在途；轮次结束等待固定思考间隔再发下一轮。

## 2. 两类工作负载（每份曲线单独冻结；换字段=另一份结果）

| 字段 | 短文本档 | 典型工具档 |
|---|---|---|
| 模型 / 协议 / 流式 | `flash` / Responses / stream=true | 同左 |
| 思考档 | 待冻结（建议 `low`；`off` 语义见 DIFF-01） | 待冻结 |
| 输入规模 | 固定短探针（标记回显） | 固定短指令 + 工具定义 |
| 输出上限 | 冻结（建议 256，覆盖隐藏推理） | 冻结（建议 256 首轮 / 128 次轮） |
| 历史 | 固定规模**每轮重置** | 固定规模每轮重置 |
| 工具 | 无 | 本地 `add_numbers`，执行时间近零（不代表真实外部工具） |
| 每轮请求数 | 1 | 2（首轮调用 + 回填后最终回答） |
| 思考间隔 | 待确认（示例 5s；0s 标“持续忙碌用户”） | 待确认 |
| 凭据模式 | 单 key（现状）→ 结果仅代表单 key 可见容量 | 同左 |
| 比例/种子 | 纯文本 | 纯工具；混合另立 |

> 若业务需要累积历史，单开一份增长历史负载并记录增长，不混入同一曲线。
> 若需多用户独立 key 或租户/模型限流信息，须先补齐，否则容量只作单 key 观测。

## 3. 分档与窗口

### A. 试运行（每份负载 1 次）
- 单用户少量样本确认请求、断言、计量、失败记录、客户端资源无瓶颈；不产出最大用户数。

### B. 寻找边界（CAP-02/03）
- 档位：示例 `1, 5, 10, 20, 50, 100`，**按已确认的最高测试负载截断**；未确认前不跑 >10。
- 每档暖机单列；正式阶段**≥2 分钟且 ≥30 全部尝试轮次**（两条件都满足）。
- 阶段最晚发起时间（示例 10 分钟）；超时记测量不足；所有请求有超时；发起与排空分开计时。
- 遇首个不达标档记边界；非单调须复核时段/配额/路由/客户端，不把偶然高档当可靠容量。

### C. 持续复核（CAP-04）
- 对候选最高达标档与首个失败档：各 **≥2 个独立窗口，每窗口 ≥10 分钟且 ≥100 轮次**；窗口间排空/低负载恢复检查。
- 报告逐分钟统计与首末趋势，不用整段平均掩盖尾部恶化。

### D. 开放到达（CAP-05）
- 在候选吞吐附近取低/目标/高三档到达率；正式 ≥2min 且 ≥30 轮次；设最大在途/队列上限，达上限记拒绝，不静默丢弃；记录计划到达/实际发起/完成/排队等待。

## 4. 停止条件与排空/恢复（CAP-06）

- 停止：达最大负载 / 明确失败边界 / 压测机受限 / 服务方中止 / 用户暂停。
- 停止发起后等在途完成或按期限关闭；以基线低负载发 ≥10 个健康轮次确认脱离压力；延迟恢复按冻结容差判（未恢复保留异常）。
- 监控压测机 CPU/内存/连接/调度滞后与实际在途，避免把客户端瓶颈当网关边界。

## 5. 请求量与时间估算（按已测速率，供预算）

- 实测速率参考：1 用户 ≈26 轮/60s；5 用户 ≈125 轮/60s（短文本）。
- 每档预计轮次约为 `用户数 × 窗口秒数 / (整轮平均耗时 + 思考间隔)`，达到最低轮数前可能延长；请求数再乘每轮请求数。最低30/100轮不是发起上限。
- 例：思考间隔5秒、忽略服务耗时，1/5/10/20档各120秒约864轮；10/20档各两个600秒窗口约7200轮。单负载约8064轮，文本约8064请求、工具约16128请求，两种合计约24192，另加恢复、暖机及超出最短窗口部分。这是示例估算，不是执行授权。
- 为预算预留按最晚发起窗口计算的保守界限：`Σ 用户数 × (ceil(max_seconds / think_time)+1) × 窗口数 × 每轮请求数`，加基线/恢复。think_time=0没有此速率上界，必须依赖硬请求上限。
- 当前待确认模板预览：文本请求保守界限17656，工具35312；各模板硬发起预算示例30000。因此工具模板可能因预算不足提前停止，不能在未重算/批准预算前承诺完成。
- 每种负载扫描至少8分钟、持续复核至少40分钟、恢复压力至少2分钟，共至少50分钟；两种至少100分钟，另加基线/健康恢复/排空。当前模板最晚发起时间各6600秒（110分钟），两种220分钟，排空另计。不再用一个笼统时间承诺覆盖所有阶段。
- 每份执行计划的 max_requests 是硬发起预算，原子预留工具完整两请求轮次；第一请求失败时未用的预留不回收，因此实际请求可能少于预算。预算耗尽记样本不足，不能作为服务容量失败边界。费用预算由已确认最大请求数、输入规模和输出上限核算；未知计费语义保留为限制。

## 6. 待管理者/用户确认的参数（缺一不可，未知则不跑对应阶段）

1. **SLO**：成功率、完整轮次 p95、首正文 p95 的具体数值（示例 ≥99% / ≤10s / ≤2s 不是已确认值）。
2. **允许的最高测试负载**（决定档位截断点）。
3. **测试窗口与费用/配额预算**（单次窗口上限、总额度）。
4. **凭据模式**：单 key 还是多用户独立 key；账户/租户/模型限流。
5. **两类负载的输入/输出规模、思考档、思考间隔、工具场景比例**。
6. 是否需要累积历史负载、多目标（公网/内网）对照。

## 7. 执行入口（先预览，参数确认后才执行）

新入口覆盖 CAP-02文本、CAP-03工具、CAP-04独立持续窗口、CAP-06压前基线→压力→排空→恢复。工作负载每轮固定历史；工具为独立加法计算+正确call_id回填+精确最终答案。按实际HTTP重叠计算峰值，成功延迟和失败轮数分开统计，全部请求保留wire/usage/原始终态。

[文本计划模板](容量执行计划-text-待确认.json) 与 [工具计划模板](容量执行计划-tool-待确认.json) 都是 **confirmed=false**，其中SLO、最高负载、预算及恢复容差均未获确认。先复制成执行计划，按真实确认值填写 `approval_reference` 和 confirmed；不能把示例自动当授权。频控/费用受限时应降低计划规模并重新确认。

旧入口仅保留CAP-01 burst 与CAP-05开放到达，以及历史CAP-02；**不能用 `run --items CAP-03/04/06` 代替新入口**。CAP-05本次修复了真正的在途/排队上限和精确正文断言；只完成离线验证，其历史测量不能自动当作修正后实测。

```powershell
cd code
python -m llm_probe run --module cap --target tpt-gateway-public --items CAP-01 --burst-levels <截断后的档位>
python -m llm_probe run --module cap --target tpt-gateway-public --items CAP-05 --arrival-rate <r/s> --duration 120 --max-in-flight <n> --queue-limit <m>
```

结论句式（严守证据）：全档通过→“已持续验证到 N，更高未测，最大值未知”；有达标 U/失败 F→“已验证 U，边界在已测档位之间，不能声称精确最大值”；只做 burst→“已测 N 同时在途请求，无用户容量结论”；无 SLO/样本不足/非单调/客户端受限→“尚不能确认”。
