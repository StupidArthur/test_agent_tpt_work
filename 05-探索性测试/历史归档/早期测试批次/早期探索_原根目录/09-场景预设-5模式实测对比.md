## 3. 逐模式验证：是否真的体现了文档承诺的价值

### 3.1 `standard` —— 基线 ✅

轨迹显示 3 次 `pwsh` 直接调用，模型自己编排：

```
助手: Let me look at the directory F:\tpt-workspace. But sandbox is workspace-write;
      reading F: might be allowed? Let's try. Let me list .txt files directly.
工具: pwsh {"command":"Get-ChildItem -Path 'F:\tpt…"} → 20260918_180028.txt …
助手: Now extract all digit runs from each filename…
工具: pwsh {"command":"$rows = Get-ChildItem -Path…"} → 名称 数字段 和 …
助手: Verify count: 28 files. Total sum from the table. Let me double check…
工具: pwsh {"command":"$s=0; Get-ChildItem -Path …"} → 20261285137177
```

模型甚至自己做了**第二次独立验算**。答案正确，主动指出「前导零被截短」的口径问题。

### 3.2 `ptc` —— 文档价值 ✅ **明确体现**

| | `standard` | `ptc` |
| --- | --- | --- |
| 工具调用 | `pwsh` ×3 | **`run_code` ×2** |
| 耗时 | 26 s | **16 s（快 38%）** |
| token | 65.5K | **53.7K（省 18%）** |
| 步数 | 5 | **3** |

轨迹原文：

```
助手: The user wants me to scan F:\tpt-workspace again. Previously pwsh failed with
      "PTY shell exited during startup". Let me try again — maybe I can just use the
      filesystem directly via run_code? … Let's try fs.readdir …
工具: run_code  "List top-level txt files in F:\tpt-workspace via Node fs"
      → { "readdirOk": true, "total": 29, "dirs": [], "files": [ … ] }
助手: 28 txt files. Now compute: extract all digit runs from each filename …
工具: run_code  "Sum digit groups in each txt filename and ra…"
      → count = 28 TOTAL = 20261285137177 top3 = [ … ]
```

✅ 文档原话「**PTC 改变的是工具调用方式**」——实测成立：同样的能力，换成写代码组织调用，调用次数、耗时、token 三项全面下降。

✅ 额外收获：它发现 `pwsh` 挂了之后，**主动改用 Node `fs` 绕过**，任务仍然完成。这是"用程序组织工具调用"的另一个价值。

### 3.3 `minimal` —— 文档承诺 ✅ 属实，但**功能 100% 不可用** ❌

**文档承诺逐条核对**（读会话 JSON）：

| 文档承诺 | 实测 | 判定 |
| --- | --- | --- |
| 不加载 Skills | 会话内 `available_skills` **不存在** | ✅ 属实 |
| 不注入标准运行时上下文 | 会话内 `Current runtime context` **不存在** | ✅ 属实 |
| 仅提供持久化 Shell | 尝试调用 shell **18 次全部失败** | ❌ 唯一工具不可用 |

**失败详情**：

> 本会话的命令行工具连续约 18 次启动失败，报错均为 `PTY shell exited during startup`（连 `echo` 这种最小命令也起不来）。
> 同时运行时依赖加载也失败：`EPERM: operation not permitted, rename …\dsh-runtimes\.primary-runtime-XSiWI4 -> …\dsh-primary-runtime`。

**耗时 2 分 25 秒，零产出。**

⚠️ **这解释了旧包的 P-001**（"Agent 内 PowerShell 执行失败 exit 3221225794"）。真正根因是**持久化 PTY Shell 不可用 + runtime 目录改名 EPERM**，而 `standard` 模式走的 `tool-pwsh` 通道是好的。

⚠️ **设计层面的放大问题**：`minimal` 把工具面砍到只剩这一个 shell，**没有任何回退**。同一个平台缺陷，在 `standard` 下只是"少个工具"，在 `minimal` 下就是**整个模式不可用**。

🟡 **未在文档中提及**：`minimal` 会话里也**没有注入记忆快照**（`记忆定位` 不存在）。文档只说"不注入标准运行时上下文"，没说记忆也一并没了。

### 3.4 `cordis` —— 生效，但本用例测不出差异 🟡

- `agentPreset = cordis` ✅ 生效
- 答案正确，**输出最详尽**：给了全部 28 个文件的数字和明细表，并主动核对排序与数值表对齐
- 耗时 30 s / 61.3K tok / 4 步

**但**：本题不涉及插件开发，`cordis` 相对 `standard` 的**唯一差异（插件开发能力）在本次测试中没有被触发**。

→ 文档里"可以编写插件来添加功能或界面"这一条**尚未验证**，需要另配一个插件类任务。

### 3.5 `factory` —— 文档价值 ✅ **明显体现**

同一个问题，输出结构与其它模式**肉眼可见不同**：

```
### 关键信息                                    ← 人设硬性要求
F:\tpt-workspace 顶层共 28 个 .txt 文件；文件名内全部数字段总和
20,261,285,137,177；其中「时间标签_20260918160030.txt」以 20,260,918,160,030 遥遥领先。

1) 全部文件名数字总和 …
2) 单文件数字和最大的 3 个 …

说明与判据：                                   ← 人设要求的"验证/判据"段
… 数字段按「文件名中连续数字字符」切分 … 前导零按数值处理 …
… 量级比第二名高约 1000 倍 —— 这是格式差异导致的，不是统计错误 …
… 未含子目录文件；若目录内后续新增或改名，结果需重算 …   ← 边界声明
```

| 人设条款 | 实测 |
| --- | --- |
| 「正文前默认输出 `### 关键信息`」 | ✅ 出现了，且是 ≤5 行摘要 |
| 「给出判据 / 验证」 | ✅ 有「说明与判据」段 |
| 「不确定内容必须体现条件和证据边界」 | ✅ 结尾声明了假设与重算条件 |
| 「安全告警卡仅用于极高风险，避免警报疲劳」 | ✅ **没有**滥用告警卡（本题非安全类问题） |
| 「不使用表格（关键信息段内）」 | ✅ 关键信息段是纯文本 |

**耗时 22 s / 51.6K tok / 3 步** —— 5 个模式里**最省 token**。

## 4. 测试中发现的问题

| # | 定级 | 问题 |
| --- | --- | --- |
| **M-01** | **P0** | **极简模式 100% 不可用**：唯一工具「持久化 PTY Shell」启动失败（`PTY shell exited during startup`）+ `EPERM rename dsh-runtimes`。因该模式无回退工具，整模式不可用。这也是旧包 P-001 的根因 |
| **M-02** | P1 | **切预设后立即新建任务，预设不生效**：第一次选 PTC 后立刻点「新建任务」，会话 `agentPreset` 仍是 `standard`；加 2 秒等待后复测即为 `ptc`。设置页 UI 显示已选中并带「新任务默认」徽标，**存在"设置已生效"的假象** |
| **M-03** | P1 | **PTC 模式说明与实际存在偏差**：文档写「当前内置预设让 Agent 通过 `run_code` 编写 **TypeScript 程序**」，实测未体现语言/SDK 细节，仅确认走 `run_code`；且文档写「当前 PTC 预设**未启用** `workflow` 工具」——这类实现状态混在用户文档里易被当作缺陷 |
| **M-04** | P2 | **极简模式不注入记忆快照**，文档未提及。文档只说"不注入标准运行时上下文" |
| **M-05** | P2 | **自定义预设缺少 `模式说明` / `如何使用`**：工厂模式卡片只有「查看配置」，5 个预设里唯一的例外 |
| **M-06** | P2 | **极简模式两页签内容完全相同**且无示例任务，其余 4 个都有 |
| **M-07** | — | `cordis` 的核心价值（插件开发）本次未覆盖，需另配任务验证 |

## 5. 结论

**问题 1：5 种模式在使用中真的有区别吗？**
**有，而且可量化。** 同一道题、同一模型、同一权限下：

- **调用方式**：`standard`/`cordis`/`factory` 用 `pwsh` 直调，`ptc` 用 `run_code`
- **效率**：`ptc` 比 `standard` 快 38%、省 18% token、少 2 步
- **输出形态**：`factory` 强制带 `### 关键信息` 摘要块 + 判据段，与其它模式结构完全不同
- **上下文面**：`minimal` 不注入 skills / runtime context / 记忆快照

**问题 2：它们真的体现了文档承诺的价值吗？**

| 模式 | 文档承诺 | 是否兑现 |
| --- | --- | --- |
| `standard` | 通用基线 | ✅ |
| `ptc` | 改变工具调用方式 | ✅ **明确兑现，且有量化收益** |
| `minimal` | 做减法、作对照基线 | ⚠️ 减法属实，但**功能不可用** |
| `cordis` | 可写插件、造模式 | 🟡 未覆盖到 |
| `factory` | 行业人设与安全约束 | ✅ **明确兑现** |

**总体：文档描述与实现基本吻合，3 个模式（standard / ptc / factory）完全兑现承诺；`minimal` 因平台缺陷不可用；`cordis` 需要专门任务才能验证。**
