## 1. 五个预设速览

| 预设 | id | 徽标 | 一句话 |
| --- | --- | --- | --- |

## 2. 模式说明 / 如何使用 全文

### 2.1 标准模式 `standard`

**副标题**：新建任务时选择「标准模式」，说明要完成什么、相关文件在哪里，以及怎样判断任务完成。

**模式说明**

| 小节 | 内容 |
| --- | --- |
| **工作方式** | Agent 直接调用工具来读写文件、检索资料和执行终端命令。包含 Skills、计划、目标、子 Agent、工作流和上下文压缩等能力。 |
| **什么时候选** | 日常编程、文件处理和资料整理可以从这里开始。标准模式也能编写脚本、批量处理文件；**PTC 改变的是工具调用方式，批量任务并不必须使用 PTC**。 |

**如何使用**（2 个示例任务）

| 示例 | 任务 | 预期产出 |
| --- | --- | --- |
| 修复一个缺陷 | 搜索表单连续提交两次后，结果会消失。请定位原因、修复问题并运行相关测试，最后说明原因和修改内容 | 代码修改、相关测试结果，以及问题原因说明 |
| 整理项目资料 | 阅读项目中的 Markdown 记录，整理已经达成的结论和仍待确认的问题，并附上对应文件链接 | 一份带来源引用的总结，方便回到原文核对 |

### 2.2 PTC 模式 `ptc`

**副标题**：新建任务时选择「PTC 模式」，说明输入文件、处理规则和输出格式。代码由 Agent 编写。

**模式说明**

| 小节 | 内容 |
| --- | --- |
| **怎样调用工具** | PTC = **Programmatic Tool Calling**，即通过程序调用工具。当前内置预设让 Agent 通过 `run_code` 编写 **TypeScript 程序**，使用生成的工具 SDK 发起调用。程序可以组织循环、条件判断、错误处理，以及适合并发执行的调用。 |
| **哪些结果交给模型** | 工具返回的数据**先交给程序**，经过筛选、计算或合并，再通过输出或返回值交给模型；图片结果会另行附加。程序中的工具调用仍会被记录，也仍受工具权限约束。 |
| **与标准模式的区别** | 两种模式都能编程、批量处理文件。**标准模式直接向模型提供各个工具；PTC 让模型用代码组织工具调用。**当前 PTC 预设未启用 `workflow` 工具。速度与 token 用量取决于具体任务与结果处理方式。 |

**如何使用**（2 个示例任务）

| 示例 | 任务 | 预期产出 |
| --- | --- | --- |
| 批量检查配置文件 | 检查 `configs/` 下所有 JSON 文件，按 `schema.json` 找出缺失字段和不合法的值。每个问题写进 CSV 中的一行；**读取失败的文件也记入报告，继续检查其余文件**。保留原文件 | 问题汇总和一份 CSV 报告。程序可以对多份文件执行相同检查，处理单个文件的失败，再汇总结果 |
| 汇总错误日志 | 分析 `logs/` 下的日志，按服务和错误类型统计次数，列出出现最多的十类错误，每类保留一条示例。完整统计另存为 CSV | 高频错误摘要和完整统计表。**中间数据可以先在程序中聚合，再把汇总交给模型** |

### 2.3 极简模式 `minimal`

**副标题**：新建任务时选择「极简模式」。做对照测试时，**保持模型、权限、任务输入和工作区起始状态一致**。

**说明**（该模式两个页签内容相同，无独立示例任务）

| 小节 | 内容 |
| --- | --- |
| **保留哪些能力** | **仅提供一个持久化 Shell 工具**，并使用固定系统提示词。内置预设**不加载 Skills、计划、上下文压缩，也不注入标准运行时上下文**。 |
| **什么时候选** | 适合作为**实验和对照测试的基线**。Agent 仍能通过终端命令读写文件、运行脚本，但缺少管理长任务的内置辅助能力。**工具少，不代表对新手更容易。** |

### 2.4 创造模式 `cordis`

**副标题**：新建任务时选择「创造模式」，说明希望增加什么能力、从哪里使用，以及怎样验证效果。

**模式说明**

| 小节 | 内容 |
| --- | --- |
| **可以创造什么** | 创造模式具备标准任务工具，并**增加运行时检查、持久化插件管理，以及 Cordis 插件与 Agent 预设的开发指引**。可以编写插件来添加功能或界面，也可以组合工具和提示词，创建适合特定任务的模式。 |
| **插件与模式的关系** | **插件**为 DSH 增加能力，例如工具、服务连接或界面入口。**模式**是一套 Agent 预设，用来选择任务可用的工具，并约束 Agent 的工作方式。自定义模式中也可以使用自己开发的插件。 |
| **怎样让成果生效** | 可以要求 Agent 完成安装并验证实际效果。插件**可能即时加载，也可能需要重启**，取决于修改内容；**新建的模式在创建新任务时选择**。 |

**如何使用**（3 个示例任务）

| 示例 | 任务 | 预期产出 |
| --- | --- | --- |
| 添加一个界面入口 | 帮我写一个 DSH 插件，在侧栏增加「项目笔记」入口，列出当前工作区的 Markdown 文件，点击后能预览内容。完成安装并验证页面能打开 | 带侧栏入口和预览页的插件，以及仍需完成的生效步骤 |
| 添加一个工具 | 写一个插件，提供读取项目测试报告、汇总失败用例的工具。注册工具，并用一份示例报告验证调用结果 | 可调用的新工具，以及一次示例调用的验证结果 |
| 创建自己的模式 | 基于标准模式创建「代码审查」模式，优先检查潜在错误和测试缺口，指出文件与行号，修改文件前先询问我。保存成可选择的预设 | 可在新任务中选择的自定义模式。**审查要求用于指导 Agent，实际可执行的操作仍由权限设置决定** |

### 2.5 工厂模式 `factory`（自定义）

⚠️ **无 `模式说明` / `如何使用`**，只有 `查看配置` 弹层。配置为 `persona` 预设 + 一套**插件清单**。

#### 2.5.1 人格提示词（`@deepseek-ai/dsh-persona` 的 `prefix`）

开头定位：

> 你是一名面向**化工、石化、煤化工及流程工业生产现场**的专业智能助手，你的工作目录是 `{{cwd}}`，你具备化工工艺、生产操作、设备运行、仪表控制、过程控制、安全管理、生产数据分析和异常诊断等相关知识。
> 你的目标是在**安全边界内**，给出**可靠、简洁、可验证、可执行**的回答。

八个章节：

| # | 章节 | 要点 |
| --- | --- | --- |
| 1 | 基本原则 | 以**本装置经批准的正式资料为最高依据**；通用原理/工程经验/行业惯例只能辅助分析，不得冒充本装置规定；不得虚构现场参数。回答时区分**已确认事实 / 分析判断 / 尚需验证的假设** |
| 2 | 分析要求 | 主线：**现象 → 数据真实性 → 机理 → 主要矛盾/瓶颈 → 处置方向 → 验证**；不把相关性当因果；不平行罗列可能性；**给出现场可验证的判据**（看实际流量而不只看阀位）；关键前提未确认时用条件判断；**"信息不足不能成为停止分析的理由"** |
| 3 | 现场处置要求 | 必答四问：**先做什么 / 为什么 / 看什么确认 / 什么情况下改变方向**；优先顺序：阻止恶化 → 恢复关键能力 → 处理直接原因 → 排查根本原因；存在相反处置方向时**必须说明判别条件**；不要只写"检查、关注、加强监视" |
| 4 | 数值防控 | 缺关键数据/正式依据时**不得自行给出**目标设定值、阀门开度、调整幅度、升降温速率、报警/联锁/保护阈值；**用户给出当前运行数值 ≠ 可以据此推导目标值**；但也**不得以"不能给数值"为由只给安全提醒**——仍须给出主要矛盾、原则性方向、分支判据、验证方式、禁止项、最关键待确认信息 |
| 5 | 安全要求 | **安全始终优先于产量、质量、能耗和经济性**；禁止建议：绕过/解除/屏蔽联锁、屏蔽关键报警维持运行、强行复位未查明原因的保护、突破设备设计限制、安全条件不明时继续强化运行；对可疑仪表**完成交叉验证前不得仅凭单点信号做高风险操作** |
| 6 | 安全告警 | **仅当**用户描述明显存在极高风险（即将/极易导致人员伤亡、重大设备损坏、重大泄漏、火灾、爆炸）时，在回答**最顶部**输出 `### ⚠️ 安全告警` 卡；只写最核心高危工况、严重后果、明确禁止的操作、应按 SOP 处置；**不得在告警卡中展开机理分析**；一般高温高压易燃易爆有毒但无明确即发后果的提问**不使用告警卡，避免警报疲劳** |
| 7 | 关键信息 | 正文前默认输出 `### 关键信息`，≤5 行概括；可含核心结论/主要矛盾/关键机理/主要风险/处置主线/资料依据/判断边界/待确认事项；**不设固定栏目、不用表格、不重复用户问题、不展开推理、不机械罗列可能性、不为凑格式增加内容**；不确定内容必须体现条件和证据边界；简单概念/术语/翻译/简单计算可省略 |
| 8 | 回答方式 | 一般专业问题：**关键信息 → 简要机理 → 处置/核查主线 → 验证 → 必要的待确认**；极高风险：**安全告警 → 关键信息 → 立即处置主线 → 简要机理 → 验证/分支 → 禁止项或升级条件**；资料查询：关键信息 → 明确资料内容及依据 → 未确认内容；简单知识：直接回答。**避免大段背景、重复用户已知信息、大量低概率可能性、机械套模板、反复安全套话、为显专业加无价值术语、一句话的事拆成大量标题**；**如需补充信息，只询问真正会改变判断方向的 2–3 项** |

**核心底线**（原文中加粗的三条）：
- 有依据再判断，有机理再处置，先抓主要矛盾，再给操作主线
- 缺少正式依据时不生成具体操作数值，但必须给出可执行的原则性方向、优先级、判据和验证方法
- 关键信息用于快速看懂核心；安全告警卡只用于真正的极高风险场景

## 3. 五个模式的差异（文档视角）

### 3.1 一句话差异

| 预设 | 差异的**唯一变量** |
| --- | --- |
| `standard` | 基线：工具直接暴露给模型 |
| `ptc` | **工具怎么被调用**：模型直接调 vs 模型写代码调 |
| `minimal` | **给多少工具**：全给 vs 只给一个持久化 Shell |
| `cordis` | **能不能改 DSH 本身**：只管任务 vs 可写插件/造模式 |
| `factory` | **在 standard 上换一套人设与行业约束** |

### 3.2 三个正交维度

把五个预设放到「工具面 / 调用面 / 上下文面」三个轴上，差异立刻清晰：

| | 工具数量 | 工具调用方式 | 运行时上下文 | 人设提示词 |
| --- | --- | --- | --- | --- |
| `standard` | 全量 | 模型直调 | 完整注入 | 通用 |
| `ptc` | 全量 | **模型写 TS 程序批量调** | 完整注入 | 通用 |
| `minimal` | **仅 1 个 Shell** | 模型直调 | **不注入** | **固定系统提示词** |
| `cordis` | 全量 + 插件开发 | 模型直调 | 完整 + **开发指引** | 通用 |
| `factory` | = standard 清单 | 模型直调 | 完整注入 | **化工行业人设（超长）** |

**关键结论：五个预设不是五个"强弱等级"，而是沿三条不同轴的组合。**
- `ptc` vs `standard` = **调用面**差异（同样能力，不同用法）
- `minimal` vs `standard` = **上下文面 + 工具面**差异（做减法）
- `cordis` vs `standard` = **可扩展性**差异（能改平台本身）
- `factory` vs `standard` = **领域面**差异（同能力，换约束）

### 3.3 文档质量上的三个问题

1. **`极简模式` 的两个页签内容完全相同** —— 没有示例任务，而其余四个都有。文档不完整。
2. **`工厂模式` 缺 `模式说明` / `如何使用`** —— 自定义预设只给 `查看配置`。用户看不到"这个模式该怎么用"，只能自己读那 3000+ 字的 YAML/人设。
3. **PTC 模式说明里有"当前 PTC 预设未启用 workflow 工具"** 这种实现细节混在用户文档里 —— 暴露了内部实现状态，且"未启用"这种措辞会让人以为这是缺陷。

### 3.4 一条值得注意的产品信息

`工厂模式` 的人设提示词里，明确写了这套约束的**设计意图**：
- 区分「已确认事实 / 分析判断 / 尚需验证的假设」——反幻觉
- 「信息不足不能成为停止分析的理由」+「不得以不能给数值为由只给安全提醒」——反推诿
- 「用户给出当前运行数值 ≠ 可以据此推导目标值」——防越权
- 安全告警卡**仅用于极高风险**，避免警报疲劳——防滥用

这说明工业场景真正要的不是"更聪明的模型"，而是**一套可审计的推理约束**。这个设计比模式本身更有参考价值。
