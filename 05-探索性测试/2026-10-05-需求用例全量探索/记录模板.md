# 执行与审查记录模板

所有字段是记录格式说明，不是实测示例。不要把模板复制为已执行证据。`执行记录/<case_id>.json`已预建；保留其来源哈希和编号，每次尝试向`attempts`追加对象，不覆盖旧尝试。

用户确认用户体系未实现、连接器本轮不可测：相关74条已标暂缓，不需填写虚构尝试。其他功能合理查找后缺入口，在阻塞原因写“目前没有发现入口”；实际操作显示占位或未开放时记录“测下来没有实现”及对应现象。开发状态差异不自动算缺陷。

## 一次执行尝试

```json
{
  "attempt_id": "<case_id>-A01",
  "started_at": "<ISO8601时间含时区>",
  "ended_at": "<ISO8601时间含时区>",
  "environment_id": "ENV-001",
  "surface": "UI/CDP、独立API或执行端测试宿主，填写实际表面",
  "actual_preconditions": {"account_alias": "非敏感别名", "workspace": "测试空间", "project": "已有项目", "session_id": "测试会话ID", "model": "实际低级模型名称", "permission": "实际权限", "fixtures": ["本轮夹具路径或ID"]},
  "input": "实际脱敏输入，含本轮唯一标记",
  "actual_steps": ["实际做了什么；定位与页面变化；没有做到的步骤也说明"],
  "wait_condition": "等待哪个业务状态；截止时间；实际是否达到",
  "checkpoints": [
    {"expected_index": 1, "expected": "用例检查点原文", "observed": "观察到的事实", "verdict": "符合/差异/未验证", "evidence": ["证据/<case_id>/<attempt_id>/终态.txt"]}
  ],
  "observed_result": "实际结果及验证深度；无额外产品特性也明确说明",
  "status": "已执行-符合预期/已执行-存在差异/已执行-结论不确定/阻塞/不适用",
  "evidence": ["证据/<case_id>/<attempt_id>/终态.txt"],
  "difference_ids": [],
  "notes": "环境因素、未验证边界及下一步"
}
```

顶层`status`指当前可交接结论，`latest_attempt_id`指向最新尝试。通过必须所有检查点已验证且有直接证据；未达到的检查点不能从数组中删掉。历史失败后本轮成功，保留历史尝试、差异和复核解释。

阻塞在顶层填`blocker`：`reason`、`missing_dependency`、`evidence`、`next_action`；只完成了部分步骤时追加尝试，逐项标未验证。不适用填`applicability_reason`：实际包或范围证据、理由、待双方确认。不适用不能由“找不到控件”单独得出。

## 差异记录

在`差异与问题登记.md`创建永久编号，并在涉及case的`differences`同步填记录或引用。每个已确认偏离必须登记，即便认为实现更合理。

```json
{
  "difference_id": "DIFF-001",
  "case_ids": ["实际case编号"],
  "attempt_ids": ["实际尝试编号"],
  "category": "实现差异/可能的设计演进/版本冲突/需求不清/环境限制/自动化问题/疑似缺陷",
  "requirement": {"file": "原文路径", "section": "章节或行号", "version_status": "有效性待核实", "expected": "检查点"},
  "observed": "事实",
  "impact": "用户影响；无明确问题也说明",
  "interpretation": "判断及未知项；根因假设单独写",
  "evidence": ["实际证据路径"],
  "reproduction": "首次及对照复核结果",
  "disposition": "待审核/需补证/撤回候选（保留历史）",
  "review": {"assistant": null, "user": null, "final_decision": "待双方审核"}
}
```

疑似缺陷另用`CAND-001`永久编号，关联DIFF与实际触发序列、合理预期、影响、最小复现、正常对照、环境排查、证据和未知项。不要只写“失败了”。同一根因未确认的问题可以关联多个case，但每条case的结果单独保留。

## 产品特性记录

```json
{
  "feature_id": "FEATURE-001",
  "statement": "本包当前实际行为",
  "case_ids": ["实际case编号"],
  "attempt_ids": ["实际尝试编号"],
  "environment_id": "ENV-001",
  "verified_depth": "入口/反馈/业务闭环/恢复",
  "scope_and_limits": "适用账号项目版本；未验证部分",
  "evidence": ["实际证据路径"],
  "relation_to_design": "符合/有差异/无文档说明",
  "review_status": "待双方审核"
}
```

每条case的`product_observations`必须保留观察，至少含行为、范围、深度、证据、是否有额外特性。复用同一特性编号可以，但不能缺本case自己的执行结果。

## 证据索引行

逐行追加到`证据/索引.jsonl`。每行是一个完整JSON对象；不存在的截图和空日志不能用作证据。

```json
{"path":"证据/<case_id>/<attempt_id>/终态.txt","case_id":"实际case编号","attempt_id":"实际尝试编号","captured_at":"ISO8601","type":"DOM/截图/脱敏响应/文件回读/日志/trace","proves":"直接证明哪个检查点","redacted":true,"sha256":"实际文件SHA256"}
```

## 双方审核

顶层`review.assistant`与`review.user`分别记录审核者、时间、意见、结论及具体批准范围。`final_decision`由双方完成后记录；有分歧先保留待讨论。执行Agent不能填两方意见冒充审核。入库只能搬获批的具体内容，并保留本任务原始记录。
