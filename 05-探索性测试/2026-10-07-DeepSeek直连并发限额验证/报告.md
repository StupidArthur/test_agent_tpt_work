# DeepSeek 直连并发限额实测（待审）

## 结论

本账号已验证 100 个请求重叠且全部完整返回；未验证 2500 并发。500 请求轮出现余额关联 HTTP 429，服务端原文报告当时并发 237、余额对应限额 225 或 236。最后一轮也出现限额 180、201、203，不能将其简化成固定 225 上限。

官方公开页面给出账号级 flash 默认 2500、超限 429，但查阅的限速、价格页面未给出恢复 2500 所需余额或换算公式。需要官方确认余额门槛；不能按单点观测线性推算充值金额。

## 分轮结果

|计划请求数|HTTP 200|HTTP 429|未取得 HTTP 状态|完整 SSE|客户端已收 200 且未读完峰值|耗时|
|---|---:|---:|---:|---:|---:|---:|
|10|10|0|0|10|10|6.126 秒|
|100|100|0|0|100|100|6.112 秒|
|500|237|263|0|237|237|6.442 秒|
|2501|525|559|1417|206|319|134.419 秒|

2501 轮 525 个 HTTP 200 中有 319 个未完整结束，存在客户端读取异常。因此不能把 525 计为成功，也不能把客户端 pending=2501 计为服务端 2501 并发。该轮在余额限流条件下不具备验证默认上限的效力。未取得 HTTP 状态的错误同样不能归为服务端拒绝。

共 3111 次尝试，822 个明确 HTTP 429，553 个完整 SSE。取得 usage 的响应累计输入 15889、输出 566272 token；未完整结束的请求可能仍有账单消耗，此数字不是最终账单总量。

## 可复盘证据

- `wave-10.json`、`wave-100.json`、`wave-500.json`、`wave-2501.json`：逐请求编号、时间、状态、usage、错误及响应哈希。
- `responses/`：完整读取的原始响应；读取异常时没有完整响应文件，对应错误保留在 wave 记录。
- `summary.json`：错误原文分布及汇总；`evidence-index.json`：证据路径、SHA-256、归属。
- `code/test_limit.py`：本轮实际执行代码，无重试，未变更账号身份。

## 方法改进与后续前置

本轮脚本在 500 请求轮完成后立即自动进入 2501 请求轮，人工检查到余额限流时最后一轮已发出。后续升档必须增加 429/不完整响应停止门禁，并在大批次前确认账号实际额度与客户端连接能力。本次不再追加请求，不充值，不推算不存在的余额公式。

要验证 2500/2501 边界，需要官方确认该账号余额已满足默认额度，并尽量保证账号无其他调用；客户端需先确认可承载该连接规模。实际服务端未完成数量应结合 429 原文与响应时间线判断，不只看提交数量。
