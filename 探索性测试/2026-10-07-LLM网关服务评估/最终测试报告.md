# LLM 网关最终测试报告

日期：2026-10-07。  
对象：TPT 公网 LLM 网关，主力模型 `flash`。  
状态：基于截至当前 main 已提交证据的离线整合；本报告未新增任何网络请求。

> 本报告按长期方案的新口径组织：先看用户体验，再看通用性能；网关服务容量与 Agent 任务容量分开。历史 36 项、DIFF 和原始证据保留在附件及各探索任务，不再作为正文主结论。

## 一、结论摘要

|问题|当前结论|
|---|---|
|核心网关能力能否供 TPT Work 调用|已测 Responses、Streaming、History、Tool Calling、Incomplete Handling、Authentication 均有通过证据；不等同于完整 UI 端到端验收|
|普通短请求体验|最新 Responses 单并发正式样本 30/30；TTFT/E2E p95 均约 **0.437s**|
|网关服务 3 秒容量|初筛已验证 **55** 个同时活跃简单请求用户；60 档超过 3s；规划总用户约 **275**|
|网关服务 5 秒容量|初筛已验证 **80**；85 档超过 5s；规划总用户约 **400**|
|网关服务 10 秒容量|初筛已验证 **200**；210 档超过 10s；规划总用户约 **1000**|
|轻量工具 Agent 参考容量|3/5/10 秒分别 **20 / 40 / 60** 个同时活跃 Agent；仅本地加法双请求链，不代表真实 standard Agent|
|真实 standard Agent 体验|单用户 30 任务仅 **27/30** 满足完整任务断言；任务 p95 **28.781s**，首有效内容 p95 **8.312s**；58/58 网关请求本身均 HTTP 200 且 completed|
|真实 standard Agent 用户容量|**尚未测定**。当前单用户任务质量/耗时基线尚不足以给 3/5/10 秒 Agent 容量|
|长上下文影响|新内容场景 E2E p95：约 500 token **0.797s**、28.79K **3.891s**、57.54K **7.281s**；上下文增长对等待影响明显|
|生产推荐容量|**尚未最终验收**。55/80/200 是容量曲线初筛结果，尚缺关键边界的持续窗口复核|

当前最有用的管理结论是：

> **对于 TPT Work 主协议 Responses 的简单短请求，在单 key、flash/low 的当前实验负载下，3/5/10 秒体验线分别初筛到 55 / 80 / 200 个同时活跃用户；按“总用户≈同时活跃用户×5”的规划口径，对应约 275 / 400 / 1000 总用户。**

这不是“网关最多只能支持 200 人”。200 是当前 **10 秒体验线下的已验证初筛档位**；更高档的延迟已经超过 10 秒。

## 二、用户体验

### 2.1 普通请求

最新 Responses 容量补测使用 flash、reasoning.effort=low、单 key、简单短文本。单并发 30 个正式样本：

- Gateway Service Success Rate：100%；
- TTFT p95：0.437s；
- E2E p95：0.437s。

短回答在低负载下反馈很快；随并发提高，主要变化是等待时间上升，而不是立即出现大量 HTTP 错误。

### 2.2 网关服务容量

以下结果按新的网关服务口径离线重分类：**纯粹的 marker/措辞不完全匹配作为模型内容质量，不自动记为网关容量失败；incomplete、传输/连接、HTTP/协议失败仍记网关失败。**

|体验线|最高已验证档|首个延迟不满足档|边界|最高通过档服务成功率|E2E p95|×5规划总用户|
|---|---:|---:|---|---:|---:|---:|
|≤3s|55|60|55～60|99.394%|2.969s|275|
|≤5s|80|85|80～85|99.583%|4.906s|400|
|≤10s|200|210|200～210|99.500%|8.469s|1000|

对应首失败档：

- 60：服务成功率约 100%，但 E2E p95 3.875s；
- 85：服务成功率约 99.608%，但 E2E p95 6.141s；
- 210：服务成功率约 99.841%，但 E2E p95 11.812s。

因此当前容量首先是**延迟边界**，不是错误率边界。

### 2.3 轻量工具 Agent 参考

todo_2 还验证了“LLM → 本地 add_numbers → LLM 最终答案”的两请求工具链：

|体验线|最高已验证同时活跃 Agent|首失败档|边界|×5规划数|
|---|---:|---:|---|---:|
|≤3s|20|25|20～25|100|
|≤5s|40|45|40～45|200|
|≤10s|60|75|60～75|300|

这组数据说明工具往返会明显降低同延迟目标下的并发容量，但工具几乎零耗时、上下文较轻，**不能作为 TPT Work standard Agent 的正式容量数字**。

### 2.4 真实 standard Agent

真实 standard Agent 负载来自产品实际采样：典型每请求约 22.5K～23.1K input token，每任务约 2 次 LLM 请求和 1 次 pwsh 工具调用，工具等待约 0.9～1.2s。

单用户正式基线：

- 30 个任务中 27 个满足完整业务断言，Agent Task Success Rate = 90%；
- 58/58 个网关请求均 HTTP 200、Responses completed；
- Agent task E2E p95 = 28.781s；
- 每请求首有效内容 p95 = 8.312s。

这说明当前主要差距不能简单归为“网关请求失败”：**网关请求层正常，但真实 Agent 的任务遵循和端到端等待仍明显弱于简单请求。**

因此本报告不把轻量工具 Agent 的 20/40/60 直接换成 standard Agent 用户容量。

### 2.5 长上下文

固定新内容上下文的 E2E p95：

|输入规模|E2E p95|相对约500 token短档|
|---:|---:|---:|
|约500 token|0.797s|1.0×|
|约28,790 token|3.891s|约4.9×|
|约57,540 token|7.281s|约9.1×|

60/60 的中部/尾部标记检查正确。对用户而言，长上下文的核心影响是等待显著增加；cache 字段只用于解释，不作为主 KPI。

## 三、通用性能指标

|通用指标|当前实测|用户体验含义|
|---|---|---|
|Gateway Service Success Rate|简单 Requests 低负载 100%；容量关键通过档均≥99%|普通请求可用概率|
|Agent Task Success Rate|standard Agent 单用户 27/30 = 90%|真实 Agent 完整任务成功概率|
|TTFT p95|简单 Responses 0.437s；完整长回答历史样本首正文 p95 约1.438s|多久开始看到有效反馈|
|E2E p95|简单 Responses 0.437s；完整长 Responses 流式 14.250s；standard Agent 28.781s|问题/任务整体完成多久|
|Output tokens/s|**尚未按新“首有效输出后”口径离线回填**|长回答开始后持续输出速度|
|E2E effective output tokens/s|完整长 Responses 流式历史均值 131.8 token/s|包含 TTFT、网络、推理的端到端效率，仅作辅助|
|Requests/s|随容量档位变化，详见 todo_2 原始曲线；不直接换算用户数|网关请求吞吐|
|Agent turns/s|轻量工具与真实 standard Agent 分开统计；不得用 Requests/s 代替|完整 Agent 工作吞吐|
|Error Rate / Distribution|高并发下需区分 incomplete、HTTP、传输和客户端连接错误|解释失败发生在哪一层|

当前没有足够原始聚合结果可以直接把历史 E2E token 速率无损改写成新定义的 Output tokens/s，因此这里宁可保留“未回填”，不伪造标准 TPS。

## 四、容量与并发补充观察

### 4.1 Chat 短请求对照

另一组 Chat Completions 短请求测试在相同 flash/low 下，将 5 秒和 10 秒边界进一步夹到：

- P95 <5s：120 通过、125 出现突破，边界约 120～125；
- P95 <10s：248 通过、250 出现突破，边界约 248～250。

这组数据只作为跨协议工程参照。TPT Work 主协议是 Responses，因此正式容量表优先使用上面的 Responses 55/80/200，不挑不同协议中更大的数字作为统一结论。

### 4.2 极高并发与客户端限制

无连接池高并发测试在约 1100 档出现大量 no_http_status / 客户端连接错误；限制连接池为 200 后，1600 应用任务两轮合计完成 3194/3200，但 E2E p95 已约 54～56s。

这至少说明两点：

1. 客户端连接/socket 能力明显参与高并发失败，不能把 1100/1600 的异常直接当成网关精确上限；
2. 即使大量任务最终完成，几十秒的 p95 也已经不满足交互式用户体验。

当前没有服务端活跃请求、排队或 upstream 指标通道，因此不能证明“服务端完全不是瓶颈”，也不能把客户端在途数当服务端真实并发。

|能力|状态|说明|
|---|---|---|
|Responses|通过（已测范围）|文本、终态及真实历史均有证据|
|Streaming|通过（已测范围）|正文、推理、工具增量和终态已解析|

这张表只说明核心 API 契约；不等同于 TPT Work 全软件端到端功能通过。

## 六、当前最重要的四个问题

### 1. standard Agent 容量仍未形成正式数字

**用户影响**：简单请求看起来容量较高，但真实 Agent 使用 20K+ 上下文、工具和多次模型调用后，体验可能完全不同。  
**当前证据**：单用户 Agent Task Success 90%，任务 p95 28.781s。  
**下一步**：先建立健康且可重复的 standard Agent 基线，再由本地 Agent 执行真实 Agent 3/5/10 秒容量曲线。

### 2. 55/80/200 仍是初筛容量，不是生产推荐容量

**用户影响**：短波次通过不能证明高峰长期运行仍维持同样 p95。  
**下一步**：只对关键边界做持续复核，不重跑整套测试；优先 55/60、80/85、200/210 中最终要采用的服务档位。

### 3. 长回答标准 Output tokens/s 尚未按新口径回填

**用户影响**：目前能看到长回答整体需要多久，但“开始回答以后生成有多快”的标准 TPS 尚未统一到新定义。  
**下一步**：优先离线从既有 SSE 时点和 usage 回填，不需要重新请求；只有原始记录确实缺失才补测。

### 4. 服务端并发/排队不可观测

**用户影响**：高并发变慢时能确认客户端端到端体验，却不能准确定位网关、通道还是上游内部排队。  
**下一步**：如需要容量根因而不仅是用户体验容量，应由服务端提供 nginx/路由/通道/队列指标或日志。

## 七、测试条件与结论边界

主要容量结论使用：

- TPT 公网网关；
- `flash`；
- Responses API；
- `reasoning.effort=low`；
- 单测试 key；
- 简单短文本固定负载；
- 每档多 wave 并发启动；
- 容量按 Gateway Service Success Rate ≥99% 与 E2E p95 3/5/10 秒分别评价。

“规划总用户=同时活跃用户×5”是当前产品规划假设，不是平台实测注册人数。

真实 standard Agent 负载与简单请求负载必须分别解读；模型、reasoning、协议、上下文、工具等待或凭据模式改变后，容量数字都可能变化。
