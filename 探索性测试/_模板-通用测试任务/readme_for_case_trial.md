## 本模式的双重目标（同时完成，互不冲突）

1. **产品测试**：严格执行原始用例，独立记录产品真实行为、预期差异、未观测断言及证据；用例预期不自动视为产品正确规范。
2. **用例验证**：判断每条用例的目标明确性、前置完整性、操作可执行性、断言有效性、可复现性、恢复完整性，以及已有工具能否真实支撑关键操作和读取。

执行前冻结 `测试用例.md` 的原始版本和编号。发现用例不合理、断言不清、样本缺失或工具问题时，**保留原始用例、失败现场及尝试**，另记候选归因与修订建议；如需验证修订方案，另存修订版本并留对应补测 attempt，不将修订后通过回填原用例。

产品不符合原始预期**不自动**代表用例不合格；产品全部符合预期也**不自动**代表用例能入库。产品缺陷、用例问题、环境/工具问题均只给出有证据的初步分类，最终由用户或指定审核者判断。

## 交付

- 执行后创建 `测试报告.md`：产品真实表现、各断言与证据、候选异常/缺陷、未验证项。
- 执行后创建 `用例评估.md`：逐条列用例问题、证据、修订建议及**建议入库 / 修订后建议入库 / 暂不建议入库 / 证据不足**。
- 记录恢复情况；入库审核结果默认待审核，**未经批准不写入 `04-测试项/`**。

## 固定规范（所有模式相同）

1. 阅读 [根 AGENTS.md](../../AGENTS.md) → [执行任务约定](../../04-测试项/执行任务约定.md) → [探索性测试技能](../../skills/exploratory-testing/SKILL.md) → [最小记录契约](../../skills/exploratory-testing/references/records.md)。
2. UI 操作、样本准备、读取和恢复按照 [工具入口](../../tools/ui-operations/README.md)；优先发现及复用已有函数，确缺能力时在本任务登记可复用函数及实际调用，勿私改共享主库。出现异常时按 [补测约定](../../skills/exploratory-testing/references/retest.md)。
3. 同一应用实例只由一个执行 Agent 操作。执行前核验并登记本机应用包/哈希、CDP、账号与模型、项目及工作目录、权限、运行依赖、工具版本、可操作范围；样本和状态有初值、备份及可验证恢复方式。
4. `测试用例.md` 同时是完整编号队列，不额外建立「任务队列.md」。首次执行前冻结编号、用例内容、断言及版本。所有已分配检查点都应真实尝试；不具备条件时记录准备动作、限制及补测条件，继续其他项，不猜测通过。
5. 逐条保留 run、attempt、前置及真实输入/操作、每个必要断言的预期与实际、读取来源、状态、证据和恢复；前次尝试、原始结果与失败不覆盖。预期不合理时标待审核，不偷偷改断言。工具成功不等于业务通过。
6. 执行时按需生成 `结果/`、`证据/`、证据索引、环境记录、调用日志、任务函数及 `恢复记录.md`，不为目录齐全创建空文件。通过项默认不截图，必要异常才截图。结果始终留在当前任务目录，带证据和归属；恢复失败及残留照实报告。
7. 交付分支/commit（适用时）、运行环境、已尝试与真实断言覆盖、符合/差异/未验证/阻塞/暂缓、产品候选异常、证据及恢复结论；报告与审核状态先写「待审核」。未经审核不将探索结果、候选缺陷、用例或工具直接并入正式库。
