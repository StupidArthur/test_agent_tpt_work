# 预设 Agent 负载容量测试阶段报告

日期：2026-10-07。范围：LLM 网关公网容量。当前阶段没有取得最大用户数结论。

## 结论

| 检查点 | 结果 |
|---|---|
| 产品预设负载提取 | `standard` Agent，10次完整任务；每次2个模型请求及1次 `pwsh` 工具调用 |
| 网关回放健康预检 | 3/3完整任务通过，6/6请求HTTP 200且完成 |
| 单用户容量基线 | 30轮中27轮满足本任务全部断言，成功率90%；58/58请求完成 |
| 首有效内容 | 58个模型请求p95为8.312秒，超过预先冻结的5秒门槛 |
| 当前已验证用户容量 | 尚无。单用户基线未达到容量扫描前置标准 |
| 5人以上负载 | 未执行；没有用失败的单用户基线继续加压 |

因此当前回答是：**最大用户容量未知，尚不能确认1人档满足本项目标准。**这不等于网关在基线时发生请求错误：58个网关请求均以HTTP 200和完整终态返回。差异来自端到端任务及首内容门槛未通过。

## 负载来源与真实性

从本机 UI 用例启动10个新的标准 Agent 任务，输入同一组虚构六个月销售数据，要求使用代码工具计算、返回月度表格/分析/结论。10/10显示完整最终答案，数值均为收入21,000、成本14,700、利润6,300、利润率30%。原始 session v4 日志、对应zstd压缩文件和各自SHA-256保存在 `负载采样/PRESET_CAP_20261007_*/`。

每个样本20个模型调用合计、每任务2个模型调用；服务usage每次输入约22.5K～23.1K token，输出约0.35K～1.1K token。思考档low、模型flash、工具pwsh。实测工具等待约0.9～1.2秒。当前正式模型回放使用安装包内 `@tpt-work/llm-tpt` serializer，从该轮session的system/user消息和工具定义重建Requests API body，并记录serializer来源和SHA-256。具体方法与适配器、预设文件保存在 `适配器快照/`。

容量回放不执行模型返回的Shell命令；收到本次真实工具调用后，等待抽样测得的工具时长，并回填已独立核对过的销售计算结果。两次模型调用、真实工具名称/参数、完整上下文长度、最终数字及答案完整性都逐轮检查。此法保留模型调用/上下文负载和工具往返延迟，但工具工作本身用安全固定夹具模拟。

## 已完成的测量

### 10个产品 UI 采样任务

- 预设名：`standard`，reasoning `low`，model `flash`。
- 任务执行时长约21～33秒，均完成；输出标记及四项汇总数值全部正确。
- 每次均有2个模型请求、1个pwsh工具调用、1次工具结果回填。
- 任务中途未改设置、未写用户文件、未触发审批。原始 session 数据只用于形成该任务的负载样本。

### API 回放预检

3个单用户完整任务共6个Responses请求，任务/请求成功率均100%。三轮整任务耗时p95为11.438秒；每个模型请求首有效内容p95为1.359秒。该小样本仅证明序列化、工具往返和业务断言链能工作，不作为容量统计。

### 单用户30轮基线

- 闭环定义：每个虚拟用户一次只跑一个完整 Agent 任务，任务结束后思考5秒。
- 正式窗口480.594秒，30轮、58个实际请求，峰值1个在途请求。
- 网关层：58/58 HTTP 200，均为Responses completed；无传输错误。
- 完整任务断言：27/30通过，3轮失败。两轮首请求返回文本答案却没有执行要求的pwsh工具；一轮工具往返后最终结果没同时满足标记、数字和报告格式断言。对应逐轮记录/调用与原始wire已存档。
- 整任务耗时：均值11.151秒，p50 9.531秒，p95 28.781秒；全部任务样本也包含以上断言失败。
- 模型请求首有效内容p95 8.312秒；最慢请求15.391秒。reasoning/tool/text分别记录，正文首内容缺失为null，不替换成首事件。
- 所以基线不满足任务成功率≥99%及首有效内容p95≤5秒两项；本轮并发扫描未启动。

## 判定标准与本轮执行边界

预先冻结的本项目初版验收阈值：请求及完整任务成功率均≥99%；首有效内容p95≤5秒；整任务p95≤健康单用户基线p95×1.5；开放到达客户端排队p95≤1秒且无静默丢弃/持续积压；压后至少30轮全成功，p95不超过同配置健康基线1.2倍。这些阈值是本项目定义，不是行业统一SLO。

容量流程要求先通过健康单用户基线，再测5/10/20/40档找相邻达标/不达标边界；候选边界两个独立窗口，每窗≥15分钟且≥500个完整任务尝试，并做开放到达复核。由于本轮基线不达标，扫描与持续容量窗口未执行。没有将预检样本误当成正式容量窗口。

## 建议的下一次动作

1. 检查当前 `standard` preset 对“明确要求工具调用”的遵循率，以及用例中工具调用和最终格式断言是否适合定义为任务成功。
2. 对首有效内容>5秒的样本查看缓存/非缓存usage、正文/推理/工具时点和队列指标。确认5秒SLO对该预设任务是否合适；若调整，先留理由并对新基线重新冻结阈值，不能看结果后把本轮改判为达标。
3. 修订后重新建立同一任务的30轮单用户健康基线。只有全部基线门槛通过，才继续用户数递增与持续窗口。

## 证据与完整性

- 执行接入和UI采样使用 `tools/ui-operations` 现有函数；唯一新增UI函数 `preset.readSurface` 只用于读取当前页面/iframe的可见预设与专家表面。
- 10个样本session及serializer来源保留在本任务；不覆盖产品本机原日志。
- 回放正式请求、SSE帧、解析终态、请求耗时、每轮断言及证据哈希在 `证据/` 和 `证据索引.jsonl`。
- baseline与预检汇总在 `结果/`；本报告不声称验证更高用户档或服务端容量上限。
- 产品没有进行设置更改；最后环境复核仍为 TPT Work `dsh-app://app/`、模型标准/low。
