# 测试代码分层设计（通用方法）

目标是让不同测试任务能**复用操作能力、取得可追溯的真实值，并独立判断用例**。这里是设计原则，不规定必须采用 Playwright、Python、Node.js 或某个产品的目录。

## 先按职责分离

| 职责 | 应承担什么 | 不应承担什么 |
|---|---|---|
| 产品/环境接入与操作支撑 | 连接、对象定位、协议请求、控件交互、等待、底层读取、动作日志与证据采集 | 按用例编号判断“通过”；捏造业务返回 |
| 可复用业务操作函数 | 以产品业务语义组合底层动作与读取，暴露明确参数、实际观察、错误、恢复要求 | 将“函数返回”当“产品通过”；隐含改变额外对象 |
| 测试编排与断言 | 管理场景准备与依赖、组织调用、将真实值与独立预期比较、汇总覆盖和恢复 | 复制底层定位代码或替函数填充预期结果 |
| 样本、证据与版本记录 | 管理夹具、唯一身份、原始事件、哈希、失败尝试和代码快照 | 隐式覆盖历史证据、泄露敏感信息 |

**这是逻辑分层，不强制物理目录数。** 小测试可以由少量文件承载多个职责，但接口仍要区分真实观察与判断；已有项目优先沿用现成实现和命名。避免每条用例各写一份完整的交互脚本，也避免为了分层拆碎简单函数。

## 从用例反推接口

1. 列出操作对象、合法前置、输入、需要证明的业务效果，以及恢复边界。
2. 检索已有函数：比较对象、语义、隐藏副作用、真实读取、失败处理和恢复，尝试组合已有能力。
3. 只有确认能力缺口时设计新的最小接口；优先可复用业务意图，而不是 `case123ClickButton` 之类的用例编号。
4. 将输入参数与本轮实际对象绑定；调用后同时返回动作状态、原始观察、证据引用和恢复信息。用例判断保持在编排层。
5. 导航、弹窗或资源状态发生变化后重新观察；仅对参数已知、界面稳定且无依赖读取的动作批量合并。

## 架构示意

```text
任务 / 用例 / 独立预期
       ↓
编排与断言（控制场景、检查真实值）
       ↓
业务函数接口（产品语义与可复用契约）
       ↓
操作支撑（连接 / 定位 / 执行 / 读取 / 取证）
       ↓
被测产品或测试环境

各层共同引用：夹具、事件日志、版本与恢复记录。
```

业务函数可返回“提交被接受”“读取超时”“对象不存在”及原始证据；**业务结论由测试编排层按用例逐项判断**。确定性比较可复用纯函数，不能混淆其计算结果与真实产品读值。

## 适配不同产品

UI、API、命令行和文件系统的操作支撑实现可能完全不同；通用分层不强迫这些通道共享同一连接模块。产品专属目录、当前函数名及运行命令见对应工具文档，例如 [TPT Work 共享工具架构](../../../04-测试工具/ui-operations/docs/下一轮测试代码分层设计.md)。

维护已有项目时优先尊重现有代码组织；将分层视作**职责检查表**，不是要求重建一套测试框架。
