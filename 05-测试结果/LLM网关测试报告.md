# LLM 网关测试报告

> **性质：正式落盘结果。** 执行过程、原始证据和补测记录保留在 `探索性测试/`；本文件保存当前审核后的正式结果。

日期：2026-10-07。  
对象：TPT 公网 LLM 网关，主力模型 `flash`。  
状态：基于截至当前 main 已提交证据的整合结果；Task B（standard Agent）已完成，Task A（Responses 关键边界持续窗口）推迟。

> 本报告按长期方案的新口径组织：先看用户体验，再用通用性能解释原因；**网关服务容量**与**Agent 任务容量**分开。历史 36 项、DIFF 和原始证据继续保留，但不再作为正文主结论。

## 一、结论摘要

|问题|当前结论|
|---|---|
|核心网关能力能否供 TPT Work 调用|已测 Responses、Streaming、History、Tool Calling、Incomplete Handling、Authentication 均有通过证据；不等同于完整 UI 端到端验收|
|普通短请求体验|Responses 单并发正式样本 30/30；TTFT/E2E p95 均约 **0.437s**|
|网关服务 3 秒容量|初筛已验证 **55** 个同时活跃简单请求用户；60 档超过 3s；规划总用户约 **275**|
|网关服务 5 秒容量|初筛已验证 **80**；85 档超过 5s；规划总用户约 **400**|
|网关服务 10 秒容量|初筛已验证 **200**；210 档超过 10s；规划总用户约 **1000**|
|上述容量是否已是生产验收值|**不是。** 关键边界双 10 分钟持续窗口尚未执行，因此仍是“初筛容量”|
|真实 standard Agent 单用户体验|Agent Task Success **96.67% (29/30)**；Gateway Service Success **100% (59/59)**；首反馈 p95 **5.55s**；Task E2E p95 **11.14s**|
|真实 standard Agent 3/5/10 秒容量|**没有已验证的正整数容量。** 已测 1 个活跃 Agent 即因成功率<99%且 Task E2E p95>10s 不满足三条体验线|
|真实 standard Agent 并发退化|1/2/5/10 用户 Task E2E p95 = **11.14 / 12.20 / 13.52 / 18.19s**；Gateway Service Success 始终 **100%**|
|长上下文影响|新内容场景 E2E p95：约 500 token **0.797s**、28.79K **3.891s**、57.54K **7.281s**；上下文增长显著增加等待|

当前最重要的管理结论：

> **简单 Responses 请求的 3/5/10 秒初筛容量分别是 55 / 80 / 200 个同时活跃用户；按“总用户≈同时活跃用户×5”的规划口径，对应约 275 / 400 / 1000 总用户。**
>
> **但真实 TPT Work standard Agent 在单用户下 Task E2E p95 已为 11.14 秒，因此当前 3/5/10 秒三条体验线下都没有已验证的正整数 Agent 容量。**

这两个结论并不矛盾：简单请求主要测试网关服务承载；standard Agent 每任务包含约 2 次大上下文 LLM 请求、工具往返和完整业务断言，负载明显更重。

## 二、用户体验

### 2.1 普通请求

Responses 容量补测使用 flash、reasoning.effort=low、单 key、简单短文本。单并发 30 个正式样本：

- Gateway Service Success Rate：100%；
- TTFT p95：0.437s；
- E2E p95：0.437s。

低负载下普通短请求反馈很快。随着并发增加，主要首先表现为等待上升，而不是 HTTP/协议错误大量增加。

### 2.2 网关服务容量

以下结果按 Gateway Service Success 口径重分类：marker/措辞不完全匹配属于模型内容质量，不自动记为网关失败；incomplete、传输/连接、HTTP/协议失败仍记网关失败。

|体验线|最高初筛通过档|首个延迟不满足档|边界|通过档服务成功率|E2E p95|×5规划总用户|
|---|---:|---:|---|---:|---:|---:|
|≤3s|55|60|55～60|99.394%|2.969s|275|
|≤5s|80|85|80～85|99.583%|4.906s|400|
|≤10s|200|210|200～210|99.500%|8.469s|1000|

首失败档：

- 60：Gateway Service Success 约 100%，E2E p95 3.875s；
- 85：Gateway Service Success 约 99.608%，E2E p95 6.141s；
- 210：Gateway Service Success 约 99.841%，E2E p95 11.812s。

因此当前短请求容量的首要限制是**延迟增长**，不是错误率。

但 Task A 的双窗口持续复核尚未执行，所以以上只能称：

> **Responses 3/5/10 秒初筛容量**

不能称“生产持续容量”或“精确最大容量”。

### 2.3 轻量工具 Agent 参考

轻量工具场景是“LLM → 本地 add_numbers → LLM 最终答案”的两请求工具链：

|体验线|最高已验证同时活跃 Agent|首失败档|边界|×5规划数|
|---|---:|---:|---|---:|
|≤3s|20|25|20～25|100|
|≤5s|40|45|40～45|200|
|≤10s|60|75|60～75|300|

这个场景证明“工具往返会降低同延迟目标下的容量”，但它的工具几乎零耗时、上下文很轻，只作为工程参考，**不能代表 TPT Work standard Agent**。

### 2.4 真实 standard Agent

本轮 Task B 严格复用长期方案中的 standard Agent workload：

- flash / low / Responses；
- 每请求典型约 22.5K～23.1K input token；
- 每任务典型 2 次 LLM 请求；
- 1 次 pwsh 工具调用；
- 工具等待约 0.9～1.2s；
- 固定收入/成本业务断言。

#### 单用户基线

|指标|结果|
|---|---:|
|任务数|30|
|Agent Task Success Rate|**96.67% (29/30)**|
|Gateway Service Success Rate|**100% (59/59)**|
|首有效反馈 p50 / p95|3.89 / **5.55s**|
|Task E2E p50 / p95|9.05 / **11.14s**|
|工具调用成功率|96.67%|
|LLM 请求/任务|1.97|
|失败分类|1 × `tool_not_called`|

结论：

- 3 秒线：1 个活跃 Agent 已不满足；
- 5 秒线：1 个活跃 Agent 已不满足；
- 10 秒线：1 个活跃 Agent 已不满足。

因此不要写“Agent 容量 = 0”。正确表述是：

> **在当前 standard Agent workload 与 99% 成功率要求下，3/5/10 秒三条体验线均没有已验证的正整数容量；已测 1 个活跃 Agent 即不满足。**

其中 1 次失败属于 `tool_not_called`，是模型/任务质量问题，不是网关请求失败。

#### 并发退化趋势

|同时活跃 Agent|任务数|Agent成功率|Gateway成功率|首反馈 p95|Task E2E p50 / p95|
|---:|---:|---:|---:|---:|---:|
|1|30|96.67%|100%|5.55s|9.05 / **11.14s**|
|2|30|100%|100%|6.00s|9.52 / **12.20s**|
|5|31|96.77%|100%|7.48s|11.00 / **13.52s**|
|10|34|100%|100%|10.36s|13.25 / **18.19s**|

相对单用户：

- 10 用户 Task E2E p95 约为 **1.63×**；
- 10 用户首反馈 p95 约为 **1.87×**。

这说明真实 Agent 随并发提高会继续变慢，但 1～10 用户范围内**网关服务层没有出现请求失败**；所有 LLM 请求的 Gateway Service Success 均为 100%。

因此当前真实 Agent 用户体验的主要问题是：

1. 单任务本身就重；
2. 并发进一步放大等待；
3. 模型偶发不调用要求工具。

不能把这些合并成“网关不稳定”。

### 2.5 长上下文

固定新内容上下文的 E2E p95：

|输入规模|E2E p95|相对约500 token短档|
|---:|---:|---:|
|约500 token|0.797s|1.0×|
|约28,790 token|3.891s|约4.9×|
|约57,540 token|7.281s|约9.1×|

60/60 中部/尾部标记检查正确。长上下文最明确的用户影响是等待增加；cache 只作为解释信息，不作为主 KPI。

|通用指标|当前实测|用户体验含义|
|---|---|---|

|Agent Task Success Rate|standard Agent：1用户 96.67%，2用户 100%，5用户 96.77%，10用户 100%|完整 Agent 任务成功概率；小样本中存在工具不调用波动|
|TTFT / 首有效反馈 p95|简单 Responses 0.437s；standard Agent 1→10用户为 5.55→10.36s|用户多久感觉任务开始有有效进展|
|E2E p95|简单 Responses 0.437s；standard Agent 1→10用户为 11.14→18.19s|问题/任务整体完成多久|
|Output tokens/s|**尚未按新“首有效输出后”口径离线回填**|长回答开始后的持续输出速度|
|E2E effective output tokens/s|完整长 Responses 流式历史均值 131.8 token/s|包含 TTFT、网络和推理的端到端效率，仅作辅助|
|Requests/s|standard Agent：1用户 0.140，2用户 0.279，5用户 0.613，10用户 1.053|网关请求吞吐|

Task B 的关键工程意义不是“网关失败”，而是明确证明了：

> **同一套真实 Agent workload 下，网关请求层 1～10 用户保持 100% 成功，但 Agent 端到端体验已经明显超过 10 秒。**

## 四、容量与并发补充观察

### 4.1 Chat 短请求对照

另一组 Chat Completions 短请求在相同 flash/low 下：

- P95 <5s：120 通过、125 出现突破，边界约 120～125；
- P95 <10s：248 通过、250 出现突破，边界约 248～250。

它只用于跨协议工程参照。TPT Work 主协议是 Responses，所以正式简单请求容量表继续使用 Responses 55/80/200，不挑不同协议中更大的数字作为统一结论。

### 4.2 极高并发与客户端限制

无连接池高并发测试在约 1100 档出现大量 no_http_status / 客户端连接错误；连接池限制为 200 后，1600 应用任务两轮合计完成 3194/3200，但 E2E p95 已约 54～56s。

因此：

1. 客户端 socket/连接能力明显参与极高并发失败，不能把 1100/1600 当网关精确上限；
2. 即使请求最终大量完成，几十秒 p95 已失去交互体验价值；
3. 没有服务端活跃请求、排队或 upstream 指标，不能把客户端在途数当服务端真实并发。

## 六、当前最重要的四个问题

### 1. standard Agent 的体验目标与实际负载不匹配

**现状**：单用户 Task E2E p95 已 11.14s，首反馈 p95 5.55s；Agent Task Success 96.67%。  
**用户影响**：即使只有一个用户，当前 3/5/10 秒目标都不能同时满足。  
**归因**：网关请求层 59/59 成功；主要由两次大上下文模型调用、工具等待及偶发 `tool_not_called` 共同形成。  
**下一步**：如果产品坚持 3/5/10 秒 Agent 体验，需要优化 Agent workload / 模型调用方式 / 上下文规模，而不是继续单纯压测网关。

### 2. Responses 55/80/200 仍是初筛容量

**现状**：边界已通过多 wave 扫描夹出，但 Task A 的双 10 分钟持续窗口推迟。  
**影响**：可用于规划与比较，暂不能当正式生产持续容量。  
**下一步**：只有在需要上线容量承诺时，再执行 55/60、80/85、200/210 的持续验收。

### 3. 标准 Output tokens/s 仍缺新口径回填

**现状**：已有长回答 E2E effective token rate，但新定义要求从首有效输出后计算。  
**下一步**：优先离线从历史 SSE 原始时间轴回填，不需要重新压测。

### 4. 服务端排队不可观测

**现状**：没有 nginx/路由/通道/队列的服务端采集权限。  
**影响**：能判断用户体验何时变慢，但极高并发时不能精准拆分网关排队、通道调度与上游等待。  
**下一步**：只有做根因/扩容工程时才需要补服务端观测，不影响当前用户体验容量结论。

## 七、测试条件与结论边界

简单 Responses 容量：

- TPT 公网网关；
- flash；
- Responses API；
- reasoning.effort=low；
- 单测试 key；
- 简单短文本；
- 多 wave 并发启动；
- Gateway Service Success ≥99%；
- E2E p95 分别按 3/5/10 秒评价。

standard Agent：

- flash / low / Responses；
- 单 key；
- 真实 standard workload；
- 每请求约 22.5K～23.1K input token；
- 典型 2 次 LLM 请求 + 1 次工具；
- Agent Task Success ≥99%；
- Task E2E p95 分别按 3/5/10 秒评价。

“规划总用户=同时活跃用户×5”只应用于已经通过对应体验线的容量规划。由于 standard Agent 在 1 用户即不满足三条线，本报告**不对 standard Agent 给出 ×5 用户规划数**。
